## 1. 벤치마킹·레퍼런스 탐색 (ui bowl)

원본 해석 전에, 프로젝트 도메인이 이미 드러나 있다면(예: "예약 서비스", "커머스 앱") ui bowl MCP로 유사 서비스의 실제 화면을 먼저 훑는다. 상상으로 스코프·요구사항을 판단하지 않기 위한 사전 조사다.

### 시작 전 확인

- ui bowl MCP 연결 여부를 먼저 확인한다. **연결되어 있지 않으면 임의로 건너뛰지 않는다.** 즉시 사용자를 호출해 알리고, 연결 후 진행할지 벤치마킹 없이 계속할지 확인받는다. 확인 없이 조용히 STEP 1을 이어가지 않는다.
- 연결이 확인되면 검색을 시작하기 전에 **사용자에게 원하는 특정 레퍼런스(앱·서비스)가 있는지 먼저 물어본다.** 사용자가 이름을 지정하면 `filter_by_app`으로 그 서비스부터 조사한다. 지정한 게 없다고 하면 도메인·기능 기반으로 자유롭게 탐색한다.

### 탐색 범위

- 같은 업종(category)에 갇히지 않는다. **기능이 유사하면 업종이 달라도 참고 대상이다.** 예: "정산 기능"을 보려면 금융 앱뿐 아니라 커머스·모임 앱의 정산 화면도 함께 본다.
- 도구: `search_ui_patterns`(화면 유형·플로우), `search_by_ocr_text`(실제 문구), `search_components`(컴포넌트·상태), `filter_by_app`(특정 앱 지정). category·country는 필요할 때만 좁히는 용도로 쓰고 처음부터 과도하게 제한하지 않는다.
- **최소 2~3개 서비스**를 비교한다. 하나만 보면 그 서비스의 특이 사례를 일반 패턴으로 오인할 수 있다.
- 볼 것: 이 기능·도메인에서 반복되는 화면 구성, 필수로 보이는 입력/상태(로딩·실패·빈 화면), 문구 톤. 컬러·타이포·레이아웃 디테일은 보지 않는다 — 이 하네스의 범위 밖이다(다음 화면설계 하네스 몫).

### 기록

- 결과는 `definition.md`의 "벤치마킹" 섹션에 기록한다: 서비스명, `ui_url`(출처), 관찰한 패턴 한 줄, 이번 프로젝트에 적용할지/제외할지와 근거.
- 관련 사례가 없으면 억지로 무관한 사례를 채우지 않고 "관련 사례 없음"으로 남긴다.
- 여기서 관찰한 내용을 근거로 요구사항을 지어내지 않는다 — 참고 자료일 뿐, 원본을 대체하지 않는다. STEP 3(플로우) 이후 화면 흐름을 잡을 때도 다시 참고할 수 있다.

## 2. 원본 자료 해석

원본(PRD·RFP·회의록)을 읽고 다음을 분리한다.

- **배경** — 왜 만드는가. 현재는 어떻게 하고 있고 무엇이 불편한가.
- **요구사항** — 기능적으로 무엇을 해야 하는가.
- **제약** — 예산·기간·플랫폼·기존 시스템·법적 요건.
- **비어 있는 것** — 원본에 없어서 물어봐야 하는 것.

원본에 명시되지 않은 것을 요구사항으로 승격하지 않는다. 필요해 보이면 `TBD:`로 남기고 `_handoff.md`에 모은다.

## 3. 요구사항 번호 부여

원본의 기능 요구사항을 한 줄씩 쪼개 `REQ-01`부터 붙인다.

- **한 REQ는 한 가지만 말한다.** "등록하고 관리하고 그룹에 넣을 수 있어야 한다"는 세 개로 쪼갠다. 쪼개지 않으면 STEP 5에서 "부분만 커버됨"을 잡아낼 수 없다.
- 원본 문장을 그대로 옮기지 말고 검증 가능한 형태로 다듬는다.
  - 나쁨: `REQ-03 편리하게 일정을 조율할 수 있어야 한다`
  - 좋음: `REQ-03 하나의 모임에 복수의 날짜 후보를 제안할 수 있다`
- 비기능 요구사항(성능·접근성·브라우저 지원 등)도 원본에 있으면 같은 체계로 번호를 매기되 `구분` 열로 나눈다.

## 4. 스코프 확정

`포함`과 `제외`를 모두 쓴다. 제외를 쓰지 않으면 나중에 범위 분쟁이 난다.

- 포함: 이번 범위에서 만드는 것
- 제외: 이번에 만들지 않는 것 + 그렇게 판단한 근거 한 줄
- 보류: 판단이 필요해 클라이언트에게 물어야 하는 것 (`TBD:` 표기)

## 5. 역할 정의

`users.md`에 역할별로 `ROLE-` 번호를 부여한다. 다음 세 축을 반드시 채운다.

| 축 | 내용 |
|---|---|
| 목표 | 이 역할이 이 서비스로 이루려는 것 |
| 진입 경로 | 로그인인가, 링크인가, 초대인가 |
| 권한 | 볼 수 있는 것 / 만들 수 있는 것 / 수정·삭제할 수 있는 것 |

### 역할을 나누는 기준

이름이 다르다고 다른 역할이 아니다. **권한이나 진입 경로가 다를 때만** 나눈다.
반대로 같은 이름이라도 진입 경로가 다르면 다른 역할이다.

`references/risk-patterns.md`의 `RISK-04`(공동 소유)와 `RISK-10`(미인증 진입)을 이 시점에 확인한다. 둘 중 하나라도 해당하면 역할 수가 늘어난다.
