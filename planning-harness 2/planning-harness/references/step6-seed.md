# STEP 6 — 시드 데이터와 인계

산출물: `seed-data.json`, `_handoff.md`
스키마: `schemas/seed.schema.json`
템플릿: `templates/handoff.template.md`

## 1. 시드 데이터 생성

`ia.yaml`의 엔티티 정의에서 자동 생성한다.

```bash
python scripts/gen_seed.py {프로젝트명}/01-planning
```

스크립트가 없으면 직접 작성하되, 아래 원칙을 지킨다.

### 실제 규모로 만든다

`project-profile.yaml`의 `data_scale`에 적힌 최대 건수를 쓴다. 5건짜리 더미로는 100건일 때 필요한 검색·필터를 발견할 수 없다 (`RISK-06`).

### 상태를 고르게 분포시킨다

한 상태에 몰린 더미는 쓸모가 없다. `flows.yaml`의 모든 `ST-`가 최소 2건씩 등장하도록 배분한다.
특히 다음이 반드시 포함되어야 한다.

- 빈 상태를 보여줄 수 있는 그룹 하나 (`RISK-07`)
- 부분 완료 건 (`RISK-08`) — 6명 중 4명 회신 같은
- 충돌 건 (`RISK-03`) — 같은 날짜에 두 건
- 다중 소속 건 (`RISK-01`) — 한 대상이 두 분류에 속함
- 마감 임박·초과 건 (`RISK-02`)

이 다섯이 없는 시드 데이터는 화면 설계 검증에 쓸 수 없다.

### 현실적인 값을 쓴다

- 이름: `홍길동1`, `홍길동2` 대신 실제 한국 이름 분포
- 텍스트 길이: 가장 긴 경우와 가장 짧은 경우를 섞는다. 레이아웃이 깨지는 지점을 찾기 위한 것이다
- 날짜: 과거·현재·미래가 섞이도록

## 2. 인계 문서 작성

`_handoff.md`는 다음 하네스(화면설계·디자인)와 사람이 함께 읽는 문서다.

포함할 것:

1. **산출물 목록과 경로**
2. **숫자 요약** — 화면 수, 플로우 수, 엔티티 수, 역할 수
3. **화면 목록** — `SCR-` ID와 이름만. 다음 하네스의 작업 단위가 된다
4. **리스크 패턴 대응 요약** — 해당된 패턴과 대응 화면
5. **`TBD:` 전체 목록** — 클라이언트 확인이 필요한 미결 사항. 하나로 모은다
6. **다음 단계 주의점** — 설계 시 특별히 신경 써야 할 화면과 이유
7. **검증 방식** — 스크립트 실행인지 수동 체크리스트인지

## 3. 자체 점검

- [ ] 시드 데이터가 `data_scale`의 최대 건수를 반영하는가
- [ ] 다섯 가지 필수 케이스가 시드에 포함되었는가
- [ ] 모든 `TBD:`가 `_handoff.md`에 모였는가
- [ ] `_handoff.md`만 읽고 다음 하네스가 작업을 시작할 수 있는가
