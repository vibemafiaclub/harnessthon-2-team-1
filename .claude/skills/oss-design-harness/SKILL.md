# oss-design-harness

**입력**: (Figma 패턴 파일 URL **또는** 디자인 시스템 문서 경로) + PRD(미확정 항목 포함 가능) + 출력 Figma 파일 URL
**출력**: 출력 파일의 새 페이지에 생성된 화면 세트 + 심사용 프레젠테이션 페이지 + `projects/<project>/` 산출물 3종(brief/decisions/report) + (선택, W단계) 클릭 가능한 웹 데모 Artifact 링크

**출력 파일 접근 확인**: 시작 직후 출력 파일에 페이지 3개(`Library`, `Screens/<project>`, `Presentation`)를 만들고 확인을 받는다. **실측 결함 두 가지, 반드시 지킨다:**

1. **빈 페이지를 확인 대상으로 주지 않는다.** 새로 만든 3개 페이지는 이 시점에 전부 비어 있다. 사용자에게 "이 페이지가 보이나요"라고 물으면 사용자는 "안 보인다"(사실은 "비어 있다")고 답한다 — 실측 사례. 확인용으로는 **아무 내용이나 임시 텍스트 노드 하나**(예: "여기가 Screens 페이지입니다 — 화면 생성 예정")를 각 페이지에 심어 두고 확인받는다. 확인이 끝나면 지운다.
2. **링크에 페이지의 node-id를 반드시 포함한다.** `https://www.figma.com/design/<fileKey>` 형태의 파일 루트 링크만 주면 Figma는 항상 파일 생성 시 자동으로 딸려오는 기본 첫 페이지(보통 "Page 1", 비어 있음)를 연다 — 사용자는 새로 만든 페이지를 못 보고 "아무것도 안 보인다"고 답한다(실측 사례). 반드시 `https://www.figma.com/design/<fileKey>?node-id=<페이지ID의 콜론을 하이픈으로 바꾼 값>` 형태로, 확인받으려는 페이지의 node-id를 넣은 링크를 준다. 페이지가 여러 개면 페이지별로 링크를 따로 준다(하나로 뭉뚱그리지 않는다).

사용자가 (내용이 채워진 상태로) 그 페이지를 볼 수 있다고 답한 뒤에만 생성을 계속한다.

검증된 `use_figma` 코드는 `references/figma-snippets.md`에 있다. 변수 생성, 배리언트 세트 사이징, 하단 네비, 인스턴스 텍스트 오버라이드, A단계 측정 스크립트는 **새로 짜지 말고 그대로 가져다 쓴다.**

운전자는 디자인 비전문가다(`CLAUDE.md` 운전자 전제 참조). 순서를 흉내내는 것이 아니라 각 단계가 **무엇을 판단해야 하는지**에 집중한다. 이미 확정된 것(디자인 시스템 문서, 사람이 정한 IA)이 있으면 그 단계는 "재추출"이 아니라 "승계"로 좁혀 진행한다 — 아래 각 단계 안에 조건 분기로 명시했다.

```
P 요구사항 정리 ─┐
F 패턴 추출/승계 ─┼→ [CP1 되읽기] → B 발산·수렴 → [CP2 시안] → G 생성 → [CP3 와이어] → G 마감 → A → C(Codex) → [CP4 최종] → W 웹 배포(선택)
0 정렬(조건부) ──┘                                                    ↑                          │
                                                                       └──── C 실패 라우팅 ────────┘
```

시작할 때 `projects/<project>/`를 만들고 템플릿 3종(`.claude/skills/oss-design-harness/templates/{brief,decisions,report}.md`)을 복사한다. `report.md`에 각 단계 시작 시각을 적는다.

## P단계 — PRD 인테이크 (요구사항 정리)

PRD를 읽고 아래 4개 표로 분해해 `brief.md`에 쓴다. PRD가 없거나 한 줄이면 그 한 줄을 PRD로 취급한다.

1. **화면 목록** — PRD 문장에서 화면이 되는 것을 뽑는다. 화면당 "이 화면에서 사용자가 끝내는 일" 한 문장.
2. **기능 목록** — 화면에 매핑되는 기능. 화면이 없는 기능은 "화면 미정"으로 표시.
3. **데이터 엔티티** — 화면에 보여줄 것(예: 모임, 지인, 일정 후보). 카드·리스트·폼의 내용이 된다.
4. **미확정 항목** — 아래 3상태로 분류한다.

| 상태 | 뜻 | 처리 |
|---|---|---|
| 확정 | PRD에 명시됨 | 그대로 사용 |
| 가정 | PRD에 없지만 합리적 기본값이 있음 | 기본값 적용, 가정 로그에 기록, CP1에서 한꺼번에 보여줌 |
| 열림 | 기본값을 고르면 화면이 크게 달라짐 | CP1 질문으로 올림 (최대 5개) |

**반드시 열림으로 올리는 것**: 사용자 경험(누가·언제·무엇을), 타깃 기기(모바일 웹 / 앱 / 데스크톱), 핵심 플로우의 시작과 끝, IA 구조(탭 개수·이름 — 입력 디자인 시스템 문서가 "사람 게이트 필요"로 못박은 항목이면 특히). 그 외에 모바일 웹이면 **브라우저 상단바 유무, 세이프에어리어, 하단 네비 방식**은 가정으로 처리한다.

### 질문 프로토콜 (CP1·CP2·CP3 공통)

- 질문 하나에 선택지 2~3개, 첫 번째가 추천 기본값. 각 선택지는 "그러면 화면이 어떻게 달라지는지" 한 줄로 설명한다.
- **표상이 아니라 체험이어야 한다.** "미니멀/모던/밀도" 같은 라벨형 질문 금지. 사용자 경험을 묻는 질문은 라벨이 아니라 **시나리오 서술**("퇴근길에 앱을 열어 오늘 저녁 예약을 잡는 사람" vs "집에서 여러 병원을 비교하는 사람")로, 정보 표시 방식처럼 실제로 보고 판단해야 하는 것은 **클릭 가능한 로우파이(Artifact HTML)**로 체험시킨다. IA(탭 구조)처럼 이산적 선택지는 각 후보의 구체 화면 구성을 함께 보여주는 조건에서 텍스트 선택지도 허용된다 — 후보 자체가 이미 구체적 구조로 분화됐기 때문이다. 원칙이 금지하는 것은 후보 자체가 추상 라벨인 질문이다.
- `AskUserQuestion`이 있으면 그것을 쓴다. 없으면 번호로 답하게 한다.
- 답이 없거나 "알아서"면 기본값 적용 + 가정 로그. 질문을 반복하지 않는다.
- 물은 것, 답, 기본값 적용 여부를 `brief.md` 질문 로그에 남긴다. 심사에서 "되물었는가"의 증거다.

## F단계 — 패턴 추출 / 디자인 시스템 승계

디자인 언어를 확보해 `brief.md` 패턴 스펙 섹션을 채운다. 입력이 두 갈래로 갈린다 — **먼저 어느 쪽인지 판별한다.**

### 입력이 Figma 패턴 파일인 경우 — F1·F2·F3 (추출)

**소스 Figma 파일은 읽기 전용이다.**

**F1·F2는 `pattern-extractor` 서브에이전트에 위임한다.** 소스 Figma URL과 스크린샷 저장 경로(`projects/<project>/refs/`)를 넘기면, 유형 판별(F1)과 디자인 언어 9항목(F2)을 `brief.md` 패턴 스펙 형식 그대로 반환한다. 이유: F1·F2는 여러 화면을 오래 들여다보는 조사 작업이라 메인 컨텍스트를 소모하고, 읽기 전용이라 위임해도 "Figma 생성·수정은 메인이 직접 한다"는 원칙과 충돌하지 않는다(`ref-scout`이 외부 레퍼런스를 조사하듯, `pattern-extractor`는 내부 소스 패턴을 조사한다). 메인은 반환된 표를 그대로 `brief.md`에 옮겨 적고, F3부터 직접 이어간다.

`pattern-extractor`가 참고하는 F1 유형 판별 기준(위임 시에도 메인이 결과를 검산할 수 있도록 남겨 둔다):

| 유형 | 판별 기준 | 이후 경로 |
|---|---|---|
| A. 라이브러리 있음 | `COMPONENT`/`COMPONENT_SET` 노드, 변수 컬렉션 존재 | F2에서 `get_variable_defs`로 토큰을 읽고, G에서 인스턴스 재사용. F3 생략 |
| B. 벡터 프레임만 | 프레임 안에 텍스트·도형 노드는 있으나 컴포넌트 없음 | `get_design_context`로 색·폰트·간격을 추출. F3 실행 |
| C. 스크린샷만 | 프레임이 이미지 필(rounded-rectangle 등)뿐 | `get_screenshot`을 화면별로 고해상도로 받아 눈으로 추출. F3 실행 |
| D. 토큰만 있음(화면 없음) | 페이지가 "Foundations"류 색·타이포·간격 스와치/변수 컬렉션뿐이고, 화면(스크린) 프레임·컴포넌트·아이콘이 파일에 전혀 없음 | F2의 색·타이포·간격·한글폰트 4항목은 확보되지만 형태·레이아웃 아키타입·장식·아이콘 4항목은 구조적으로 "미확인"이 된다. **F2를 그대로 다 채우려 하지 않는다** — 미확인 항목을 안고 그대로 **0단계(조건부)**로 넘어가 레퍼런스 보드나 로우파이로 그 빈 부분을 채운다. 실측 사례(2026-09-05, 토스 패턴 파일 `QjpU0wx4mg64v5UjG9h9A4`): "Foundations" 페이지 1개에 Color/Typography/Spacing 3개 프레임만 존재, 화면 프레임 0개. |

패턴 파일이 아예 없거나, 있어도 유형 D처럼 F2 9항목 중 레이아웃 아키타입·형태·장식·아이콘이 구조적으로 채워지지 않으면 **0단계(조건부)**로 간다. "패턴 파일이 있다 = 0단계 불필요"가 아니다 — 토큰만 있고 화면이 없는 소스는 절반만 F단계로 해결되고 나머지 절반은 0단계 몫이다.

**F2. 디자인 언어 추출** (역시 `pattern-extractor`가 수행) — 토큰만 뽑으면 "색만 같은 다른 앱"이 된다. 아래 9항목을 모두 적는다. 각 항목에 **어느 화면에서 봤는지** 파일명이나 노드 ID를 병기한다.

1. **색** — 배경, 서피스, 주색, 보조색, 텍스트 2단계, 상태색. hex로.
2. **타이포** — 패밀리, 제목/본문/캡션 3~4단계의 크기·웨이트.
3. **형태** — 카드 라운드, 버튼 라운드(알약/사각), 그림자 유무와 강도.
4. **간격** — 화면 좌우 여백, 카드 내부 패딩, 리스트 아이템 간격. 4pt 또는 8pt 그리드 여부.
5. **레이아웃 아키타입** — 상단바 구조(뒤로가기·제목·액션), 하단 네비(탭 수·중앙 FAB 여부), 리스트 셀 구조(아이콘·제목·메타·상태칩), 폼 필드 구조, 히어로/요약 카드.
6. **장식 요소** — 일러스트 스타일(3D/플랫), 배경 블롭·그라데이션, 아이콘 스타일(라인/필/컬러 배경).
7. **카피 톤** — 인사말, 버튼 문구 스타일(동사형/명사형), 언어.
8. **한글 대체 폰트** — 패턴 폰트가 한글을 지원하지 않으면(Manrope, Inter 등 대부분 그렇다) `listAvailableFontsAsync`로 확인해 한글 본문용 폰트를 정한다(기본: Noto Sans KR). 디자인 시스템의 웨이트 원칙(예: 300/400/600/700 래더)을 그 폰트가 제공하는 스타일명에 맞게 매핑한다(예: Semi Bold 600 → Medium이 가장 가까운 경우가 많다 — 폰트마다 다르니 `listAvailableFontsAsync`로 실제 스타일명을 확인하고 매핑한다). 숫자·영문에만 패턴 폰트를 쓸지 여부도 적는다.
9. **아이콘 소스** — 패턴의 아이콘 스타일(라인/필/컬러 배경)에 맞는 아이콘 세트를 확보한다. 순서: 소스 파일에 아이콘 컴포넌트가 있으면 그대로 / `search_design_system`으로 팀 라이브러리 검색 / Figma 커뮤니티 아이콘 킷을 복제해 임포트 / 마지막 수단으로 SVG path를 직접 `vectorPaths`로 넣는다(`references/figma-snippets.md` 참고). **점·사각형 자리표시자로 마감하지 않는다.** 심사 완성도 점수에서 바로 감점된다 — 실측 사례: 아이콘 자리표시자가 리스트형 화면 전반에 반복되면 C단계 패턴 정합성 자체가 FAIL로 판정된다(단발성이면 슬롭 항목 WARN에 그친다).

**F3. 최소 라이브러리 구축** (유형 B·C만, **메인이 직접** — 위임하지 않는다) — 출력 파일에 `Library` 페이지를 만들고 로컬 컴포넌트를 생성한다. `figma:figma-use` 스킬을 먼저 로드한다. `pattern-extractor`가 반환한 F2 표를 입력으로 쓴다.

- 필수 6종: 상단바, 하단 네비, 기본 버튼(primary/secondary), 리스트 셀, 입력 필드, 칩/태그.
- 각 컴포넌트는 오토레이아웃, F2의 색·타이포·라운드 적용, `type`/`state` 배리언트 최소 2개(pressed 포함 — 처음부터 넣지 않으면 A단계 Variant 커버리지에서 반복적으로 WARN을 받는다).
- 색과 타이포는 **변수 컬렉션**(`color/*`, `type/*`)으로 만들어 바인딩한다. A단계 토큰 검사가 이 변수를 기준으로 돈다.
- 시간 예산 초과 시 상단바·버튼·셀·입력 4종으로 줄인다.

### 입력이 디자인 시스템 문서인 경우 — F' (승계)

입력이 Figma 패턴 파일이 아니라 이미 색·타이포·컴포넌트·모바일 적용 규칙까지 문서로 확정된 스펙(예: `docs/design.md`)이면, F단계는 "추출"이 아니라 "그대로 승계"로 대체한다. **문서에 있는 값을 재판단하지 않는다.**

- F2(디자인 언어 9항목)는 문서에서 그대로 옮겨 적는다.
- F3(최소 라이브러리 구축)는 그대로 실행한다 — 문서에 값은 있어도 Figma 컴포넌트·변수는 아직 없기 때문이다.
- 문서에 "에이전트 결정 권한 경계" 같은 표가 있으면, 그 표에서 "사람 게이트 필요"라고 명시한 항목(전형적으로 IA 구조, 화면 추가·삭제)을 [CP1] 질문으로 우선 배정한다.
- 목데이터 생성 규칙이 문서에 있으면(예: 도메인 사실감·규모 사실감·엣지케이스 필수 포함 목록) 그 규칙을 그대로 따른다 — G단계에서 새로 판단하지 않는다.

---

## 0단계 — 요구사항 정렬 (조건부)

다음 중 하나일 때만 실행한다: 패턴 파일도 디자인 시스템 문서도 없다 / 패턴 파일은 있지만 F1 유형 D(토큰만 있고 화면 없음)라서 레이아웃 아키타입·형태·장식·아이콘이 채워지지 않았다 / PRD에 그 문서가 커버하지 않는 화면 유형(지도, 차트, 결제 등)이 있다 / CP1에서 사용자가 "느낌을 모르겠다"고 답했다 / 정보 표시 방식처럼 후보를 직접 체험해야 판단 가능한 지점이 남아 있다.

**유형 D일 때 0단계 소싱 범위**: F2에서 이미 확보된 색·타이포·간격·한글폰트는 재발산하지 않는다(패턴이 잠근 축 그대로 유지). `ref-scout`에게는 "레이아웃 아키타입·장식 요소·아이콘 스타일"만 좁혀서 요청한다 — 색이나 폰트가 다른 레퍼런스를 보여주면 사용자가 그 색까지 후보로 착각해 혼란을 준다.

**절대 규칙: 레퍼런스를 터미널 텍스트로 설명하고 끝내지 않는다.** 사용자는 실제 화면을 눈으로 봐야, 혹은 직접 눌러봐야 좋다/싫다를 말할 수 있다.

1. **소싱** — `ref-scout` 서브에이전트에 도메인·화면 유형·저장 경로(`projects/<project>/refs/`)를 넘겨 이미지 4~8장을 받는다. 순서: 웹 캡처(App Store/Play, Mobbin, 공식 사이트) → Figma 커뮤니티 렌더 → 직접 로우파이 스케치. PRD 자체가 이미 자유서술형 시나리오를 담고 있으면(예: "사용자들의 상황" 섹션) 그 자체도 1차 레퍼런스로 쓴다.
2. **보드/프로토타입** — 정적 비교면 `templates/reference-board.html`을 `projects/<project>/board.html`로 복사해 `REFS`를 채운다(카드마다 출처, 관찰 포인트 1~2개, 제안 방향 — "예쁘다"류 평가는 적지 않는다). 실제로 눌러봐야 판단 가능한 것(예: 그리드 히트맵 vs 채팅형 응답)은 별도 Artifact HTML로 클릭 가능한 로우파이를 만든다. `artifact-design` 스킬을 로드한 뒤 Artifact로 publish하고 링크만 준다.
3. **피드백** — 좋다/싫다 + 이유를 자유서술로 받는다. 라벨형 질문 금지. IA/플로우는 다이어그램이 아니라 시나리오 서술이나 클릭 가능한 로우파이로 체험시킨다.
4. **역추출** — 반응에서 암묵적 판단기준을 뽑되 근거(카드 번호 또는 반응 원문)를 병기한다.
   - 예 1 — "그리드는 한눈에 보이지만 인원 늘면 표가 사무적으로 느껴진다" → "정보 밀도는 낮게, 인원 확장에 안정적인 레이아웃을 선호"로 역추출.
   - 예 2 — PRD 조건란 "두 사람이 함께 쓰는 것을 전제로" → "탭 개수를 늘릴수록 두 사람이 다른 화면에 머무를 위험이 커진다"는 암묵적 제약으로 변환해 IA 축소 근거로 사용.

## [CP1] 요구사항 되읽기

터미널에 아래를 보여주고 멈춘다.

- 화면 목록(번호 + 한 문장), 가정 목록(번호), 열림 질문(최대 5개, 질문 프로토콜 적용).
- 패턴 스펙 요약 3줄(색·타이포·레이아웃 아키타입) + **소스 화면 스크린샷 또는 디자인 시스템 문서 발췌(반드시 첨부 — 텍스트 요약만으로 끝내지 않는다)**.
- "대표 사용 상황(UX)"을 묻는 열림 질문은 선택지 텍스트만으로 끝내지 않는다. 이미 캡처된 소스 화면이 있으면 그중 이 프로젝트 시나리오에 가장 가까운 화면 1~2장을 골라 "이 화면처럼 ○○ 상황을 처리하면"이라는 형태로 같이 보여준다. 소스 화면조차 없는 완전 그린필드 화면 유형이면 0단계로 넘겨 로우파이를 만든다.

답을 `brief.md` 질문 로그에 적고 B단계로 간다.

## B단계 — 발산·수렴

### 축 잠금

이미 정해진 것은 축이 아니다. `decisions.md`에 "잠긴 축"으로 적고 후보를 만들지 않는다: 패턴(또는 디자인 시스템 문서)이 이미 확정한 색, 타이포, 형태, 장식, 카피 톤.

### 열린 축 (2개로 고정)

1. **IA / 네비게이션** — 탭 구성, 홈에서 핵심 플로우까지 몇 단계인지.
2. **기능 ↔ 컴포넌트 매핑** — PRD의 각 기능을 어느 아키타입으로 보여줄지(요약 카드 / 리스트 셀 / 폼 / 칩 필터). 이 축이 서로 다른 **실패 모드**를 가지는 후보로 갈릴 때가 가장 흔하다 — 예: 같은 데이터를 그리드로 보여줄지 리스트로 보여줄지는 "인원 늘 때 가로스크롤 취약"과 "날짜 늘 때 칩 줄바꿈 취약"이라는 서로 다른 약점을 가진다.

축당 후보 2개. 후보는 로우파이(HTML/SVG 또는 Figma 와이어)로 렌더해 `board.html` 카드로 나란히 놓거나, 정보 표시 방식처럼 실제로 눌러봐야 하는 축은 클릭 가능한 Artifact로 만든다. **조합 코드(P1=1b+2a)만 텍스트로 나열하는 것은 금지.**

두 축이 서로 독립적인지 확인하는 기준: 한 축의 선택이 다른 축의 실패 조건에 영향을 안 줘야 한다.

### 도메인 전이 표 (Figma 패턴 소스가 있을 때)

소스 패턴의 화면·컴포넌트를 PRD의 화면·기능에 대응시킨다. `decisions.md`에 표로 남긴다.

| 소스 요소 | 소스에서의 역할 | 신규 서비스 대응 | 처리 | 이유 |
|---|---|---|---|---|
| 예: Task Groups 진행률 카드 | 그룹별 완료율 | 반려동물별 다음 예약 카드 | 대체 | 진행률 링 → 다음 예약 D-day로 의미 치환 |
| 예: 캘린더 날짜 스트립 | 날짜 선택 | 예약 날짜 선택 | 그대로 | — |
| 예: 85% 진행률 링 | 오늘 완료율 | — | 삭제 | 예약 도메인에 완료율 개념 없음 |

**규칙**: 소스의 도메인 단어(할 일, 프로젝트, 종목명 등)가 신규 화면에 남으면 C단계 즉시 실패다.

### 교차 비평 (페르소나 2개 고정)

- **UX 관점**: 핵심 플로우 단계 수, 엄지 도달, 첫 화면에서 다음 행동이 보이는가, **같은 정보가 한 화면에 두 번 나오는가**(예: 상단 전환 칩과 하단 목록이 같은 항목), 후보를 고르면 무엇을 잃는지(예: 리스트형을 고르면 그리드의 "한눈에 겹침 파악" 장점을 잃는다 — 이 손실을 보완할 요소를 명시).
- **개발/패턴 정합 관점**: 기존 컴포넌트(패턴 소스 또는 디자인 시스템 문서)로 구현 가능한지, 새 컴포넌트가 필요한지(적을수록 좋다). 소스 아키타입을 벗어나는 새 UI가 몇 개인가, 소스에 없는 화면 유형을 소스 문법으로 어떻게 풀었는가.
- 두 관점이 갈리면 실제 사용 규모(PRD의 정량적 조건, 예: "모임당 3~6명")를 캐스팅보트로 사용한다.

## [CP2] 시안 보드

보드 링크 + 카드 번호·제목 한 줄씩 + 추천 조합 1개를 보여주고 고르게 한다. 답이 "알아서"면 추천 조합 적용. 결과를 `decisions.md` 최종 선택에 적는다.

## G단계 — 생성

`figma:figma-use` 스킬을 로드한 뒤 출력 파일에 `Screens/<project>` 페이지를 만든다.

### G1. 와이어프레임(1차 조립) → [CP3]

라이브러리(F3 또는 소스 컴포넌트)가 있으면 회색 박스 와이어프레임은 만들지 않는다. **인스턴스로 조립한 1차 화면이 곧 이 하네스의 "와이어프레임"이다** — 구조 검토물이라는 역할은 회색 박스와 같고, 매체만 실제 컴포넌트 인스턴스로 바뀐 것뿐이다.

- 화면 프레임(모바일 웹/앱 기본 390×844, 디자인 시스템 문서가 다른 프레임 값을 못박았으면 그 값)을 세로 오토레이아웃으로 만들고 상단바 → 콘텐츠(FILL) → 하단 네비 순으로 인스턴스를 넣는다. 화면당 `use_figma` 1회, 화면들은 **한 메시지에서 병렬**로 호출한다(같은 페이지, 각 호출이 페이지를 한 번만 설정 — `figma.currentPage = page`는 동작하지 않는다, `await figma.setCurrentPageAsync(page)`만 된다).
- 텍스트는 PRD 데이터 엔티티의 **실제 같은 더미 데이터**를 쓴다("홍길동", "Lorem", "텍스트 1" 금지 — 목데이터 규칙이 디자인 시스템 문서에 있으면 그 규칙을 따른다). 소스 도메인 단어 금지.
- 전 화면을 페이지 단위 `get_screenshot`으로 렌더해 `refs/`에 저장하고, Figma 링크·페이지명·캡처 경로를 함께 보여주며 "구조가 맞는지"를 묻는다. 질문 프로토콜 적용. 답이 "알아서"면 진행.

### G2. 마감

- 디태치 금지. 인스턴스 텍스트는 오버라이드로만 바꾼다.
- **화면별 하단 네비 활성 탭**을 그 화면에 맞게 지정한다(전부 "홈"이면 완성도 감점). **폼/상세 화면은 하단 네비 자체를 생략하는 것이 정답일 수 있다** — 모임 만들기(폼)나 모임 상세(조율/확정)처럼 탭 이동보다 뒤로가기가 자연스러운 화면에서는 TopBar만 쓰고 BottomNav를 아예 안 붙인다. 이건 "활성 탭 누락"이 아니라 의도된 설계이므로 A/C단계에서 "이 화면엔 왜 활성 탭이 없냐"고 지적할 근거가 아니다 — 단, `report.md`나 화면 목록에 어느 화면이 탭 화면이고 어느 화면이 상세/폼 화면인지 구분해 적어 둔다(구분 없이 그냥 "네비 없음"이라고만 적으면 A단계 재검 때 실수인지 의도인지 헷갈린다).
- 입력 필드는 입력형(✎)과 선택형(▾)을 구분한다. 여러 라벨(예: 이름/생일/성별)에 같은 아이콘 하나를 공용으로 쓰면 의미가 안 맞을 수 있다 — 이 경우 라벨별 아이콘을 갈라 넣거나, 아예 아이콘 없이 chevron만 남기는 것도 유효한 선택이다.
- 장식(블롭·그라데이션)은 소스 화면(또는 문서에 명시된 원칙)의 면적·불투명도를 넘지 않는다.
- 엣지케이스: 핵심 리스트 화면 1개는 **빈 상태** 변형을 추가로 만든다. G1 단계에서 화면 범위를 정할 때 빈 상태를 처음부터 범위에 넣는다 — 마지막에 빠뜨리기 쉽다.
- 화면 하나 고칠 때마다 `get_screenshot`으로 확인한다.
- 컴포넌트 레벨에서 수정하면 그 컴포넌트를 쓰는 모든 인스턴스가 detach 없이 자동 반영된다 — 화면마다 개별 수정하지 말고 공용 컴포넌트(Library 페이지)를 고친다. 단, 화면 자체에 공용 컴포넌트 밖에서 직접 그린 도형(예: 헤더에 개별로 얹은 아이콘)이 있으면 컴포넌트 수정으로는 안 잡힌다 — 화면별로 한 번 더 검색한다.

### G3. 프레젠테이션 페이지

`Presentation` 페이지에 커버(서비스명, 한 줄 설명, 패턴/문서 출처) + 전 화면을 플로우 순서로 가로 배치 + 화면 사이 화살표. 심사 완성도 점수는 이 페이지에서 갈린다. **주의**: 여기 배치하는 것은 원본 화면의 `clone()`이라 라이브 링크가 아니다. G2에서 컴포넌트를 나중에 다시 고치면 이 페이지의 클론은 갱신되지 않으므로, 최종 마감 후에 마지막으로 한 번 클론해서 채운다(또는 수정 시마다 클론을 지우고 다시 클론).

## A단계 — 구조적 사실 검증

스크린샷 없이 노드 속성만으로 확인한다. `use_figma`로 페이지를 순회하는 스크립트를 한 번 실행해 결과를 `report.md`에 적는다. `references/figma-snippets.md`의 A단계 측정 스크립트를 기본으로 쓰고, 프로젝트 특성에 맞게 최소만 고친다.

| 항목 | 확인 방법 | 게이트 |
|---|---|---|
| 컴포넌트 재사용률 | 화면 내 INSTANCE 수 / (INSTANCE + 직접 그린 FRAME·RECTANGLE·ELLIPSE·POLYGON 수). 채움 없는 순수 레이아웃 컨테이너(오토레이아웃 래퍼)는 분모에서 제외 — 포함시키면 재사용률이 실제보다 낮게 나온다(실측: 포함 시 0.55, 제외 시 0.93). | **하드**: 70% 이상 |
| 토큰 준수 | `fills`/`strokes` 중 `type === 'SOLID'`인데 `boundVariables.color`가 없는 노드 비율. **알려진 함정**: `figma.createAutoLayout()`으로 만든 프레임은 기본으로 불투명 흰색 fill을 갖는다 — 텍스트를 담는 투명 컨테이너(탭 아이템, 섹션 그룹 등)에서 이 fill을 지우는 걸 잊으면 검증에서 걸리고, 같은 색 배경 위에서는 안 보이다가 다른 색 배경 위에서 텍스트를 통째로 가려버리는 시각 버그로도 나타난다. | **하드**: 90% 이상 |
| 도메인 단어 잔존 | 텍스트 노드에 소스 도메인 단어(패턴 출처의 원래 도메인 어휘) 검색. | **하드**: 0건 |
| Spacing 그리드 | 화면이 직접 그린 오토레이아웃의 padding/spacing이 F2 그리드 배수인지. **라이브러리 컴포넌트 내부 값은 제외**(소스 패턴이나 문서가 14/6 같은 값을 내부적으로 쓰는 경우가 있다). 허용값 목록에 없는 임의값(10px, 15px 같은 "적당해 보이는" 수치)이 하나라도 있으면 위반으로 기록. | 리포트만 |
| 레이어 네이밍 | `Screen/…`, `Section/…` 접두 비율. Figma 기본값(`Frame 1`, `Rectangle 2`)이 남아있으면 위반. 스크롤 가능 영역처럼 정적 스크린샷만으로 의도가 안 드러나는 노드는 이름에 의도를 남긴다(예: `filter-chips (scrollable)`). | 리포트만 |
| Variant 커버리지 | 버튼·셀·필드에 default/pressed(또는 selected) 존재. 목데이터 규칙에 상태 종류가 정의돼 있으면(예: 4개 상태) 화면에 최소 1건씩 다 등장하는지도 확인. | 리포트만 |

하드 게이트 실패는 C단계 전에 고친다.

## C단계 — 미적·게슈탈트 판단

**생성과 검증을 프로세스 수준에서 분리한다.** 이 하네스로 화면을 만드는 것은 Claude Code(메인 세션)다. C단계 판정은 **별도 프로세스·별도 모델인 Codex CLI**(`.claude/skills/oss-design-harness/scripts/codex-critic.sh`)에 위임한다. Claude 서브에이전트로 판정하면 "만든 모델이 자기 결과를 검증"하는 구조가 되어 같은 모델 특유의 판단 편향(자기 승인, 놓치는 지점이 같음)을 벗어나지 못한다. Codex는 다른 회사·다른 모델·다른 세션이므로 만드는 과정을 전혀 모른 채 결과물만 본다.

```bash
.claude/skills/oss-design-harness/scripts/codex-critic.sh \
  projects/<project>/brief.md \
  <PRD 경로> \
  <신규 화면 PNG 1장 이상> \
  -- \
  <소스 패턴 PNG 1장 이상, 없으면 디자인 시스템 문서에서 발췌한 참고 이미지나 이전 승인된 화면>
```

- `brief.md`의 "## F. 패턴 스펙" 섹션을 자동으로 읽어 프롬프트에 넣는다. 그 섹션이 비어 있으면 판정 품질이 떨어지므로 F단계를 먼저 채운다.
- **PRD 원문 전체**를 프롬프트에 그대로 넣는다(brief.md의 요약이 아니라 원문 — 요약 과정에서 유저스토리 뉘앙스나 엣지케이스가 누락될 수 있기 때문). Codex가 매번 PRD를 직접 읽고 스스로 핵심 유저스토리를 뽑아 판정하므로, 메인이 미리 뽑은 체크리스트를 넘기지 않는다 — 메인의 해석 편향이 검증에 섞이는 걸 막는다.
- stdout에 고정 포맷(`## 판정: PASS|FAIL` 등)을 낸다. 종료 코드 0=PASS, 1=FAIL, 2=실행 실패(포맷 파싱 불가 등 — 재시도 카운트에 넣지 않고 사람에게 원문을 보여준다).
- 화면이 여러 장이면 한 번의 호출에 전부 첨부한다. 여러 번 나눠 부르면 화면 간 일관성(색온도 등)을 비교할 수 없다.
- 메인은 Codex 응답 원문을 그대로 `report.md`에 옮기고, 진단 결과에 따라 라우팅만 한다. **판정 문구 자체를 메인이 다시 쓰거나 완화하지 않는다.** 특히 하드 4(상업 퀄리티)는 냉정하게 잡으라고 설계된 게이트다 — Codex가 FAIL을 내고 구체 결함을 들면 그걸 "그 정도면 괜찮은데"라고 메인이 깎아내리지 않는다.
- Codex CLI가 이 환경에 없거나(`which codex` 실패) 미로그인이면 `.claude/agents/design-critic.md`(Claude 서브에이전트)로 폴백한다. 폴백을 쓴 경우 `report.md`에 "Codex 미가용, Claude 서브에이전트로 대체 판정"이라고 반드시 명시한다.

### 판정 항목과 실측 캘리브레이션

**4개 모두 하드 게이트**(하나라도 FAIL이면 전체 판정 FAIL), Codex 프롬프트에 내장:

1. **패턴 정합성** — 소스(또는 문서가 정한 언어)와 나란히 놓았을 때 "같은 회사가 만든 다른 서비스"로 보이는가. 근거는 구체 속성(주색 면적 비율, 카드 라운드·그림자 강도, 상단바 높이감, 리스트 셀 구조, 일러스트 스타일, 하단 네비 형태)으로 든다.
   - 카드 라운드: 소스와 신규 화면의 `cornerRadius` 차이가 4px 이하면 "같은 언어"로 판정, 그 이상이면 FAIL 근거로 지목된다.
   - 아이콘·이미지 자리표시자(단색 원/사각형)가 하나라도 남아 있으면 최소 슬롭 항목 WARN, 리스트형 화면 전반에 반복되면 패턴 정합성 자체가 FAIL로 판정된다(실측 사례: "아이콘 타일이 보라·핑크 점 자리표시자로 남아 소스의 컬러 필 아이콘 문법과 다르다").
   - 하단 네비 아이콘 형태(라인 vs 필 vs 컬러 배경)가 소스와 다르면 시각적 위계는 통과해도 패턴 정합성만 별도로 FAIL 처리한다(둘은 독립 판정이다).
2. **시각적 위계** — 각 화면에서 3초 안에 "무엇을 하라는 화면인지" 읽히는가. 화면당 CTA(주 버튼)가 정확히 1개이고, 첫 시선이 가는 요소(히어로 카드, 최상단 배너)가 그 CTA와 같은 목적을 가리키면 PASS. CTA가 2개 이상 경쟁하거나, 첫 시선 요소가 CTA와 무관한 정보면 FAIL. 제목(가장 크고 굵은 텍스트) → 상태/메타(작고 옅은 텍스트) 순서로 눈이 흐르는지가 핵심이다.
3. **PRD 핵심 플로우 커버리지** — PRD의 핵심 유저스토리 각각에 대해 "지금 보여준 화면들만으로 시작부터 끝까지 완료할 수 있는가"를 유저스토리별로 판정한다. 하나라도 화면상 완결이 안 보이면 이 게이트 전체가 FAIL. PRD가 명시한 엣지케이스(예: 청첩장모임 PRD의 "중복 소속", "늦은 회신", "겹치는 모임")가 화면 어딘가에서 실제로 처리된 근거가 있는지도 함께 판정한다. **주의**: 이건 "화면 개수가 부족하다"는 지적이 아니다 — G단계에서 시간 예산 때문에 일부러 화면 범위를 좁혔다면(예: 6장 중 4장만), 좁힌 범위 안의 유저스토리가 완결되는지만 본다. 범위 밖 유저스토리를 이유로 FAIL 주면 안 된다 — 이 경우 실패 라우팅은 "방향"이 아니라 애초에 P단계에서 화면 범위 합의가 잘못됐다는 신호이므로 사람에게 먼저 확인한다.
4. **상업 퀄리티(클라이언트 관점)** — "2000만원을 주고 외주 제작사에 맡긴 클라이언트가 이 화면 세트를 최종 인도물로 받아들이겠는가"를 판정한다. 패턴 정합성·위계·플로우가 전부 PASS여도, 마감이 조잡하면(그림자 강도가 화면마다 다르다, CTA 문구 톤이 화면 간에 안 맞는다, 여백이 화면마다 몇 px씩 어긋난다) 이 게이트만 별도로 FAIL 날 수 있다 — 나머지 3개가 "구조가 맞는가"를 본다면 이건 "다듬어졌는가"를 본다. FAIL이면 반드시 구체 결함 3가지 이상을 스크린샷에서 실제로 보이는 근거로 든다. "더 세련되게" 같은 추상적 지적은 결함으로 인정하지 않는다 — 이 게이트가 느슨해지면 다른 3개 게이트가 다 PASS인 화면도 "적당히 봐주는" 판정이 나오게 되므로 가장 엄격하게 적용한다.

리포트 항목 5개, Codex 프롬프트에 내장:

- **색온도·조명 일관성** — 화면을 넘나들며 같은 역할의 영역(헤더, 리스트 배경, 탭바)이 동일한 표면 토큰을 쓰는지. 한 화면만 유독 배경이 살짝 다른 흰색/검은색을 쓰면 바로 눈에 띈다. 원인은 대개 A단계에서 걸러지는 미바인딩 하드코딩 색상이므로, C단계에서 발견되면 먼저 A단계 재검부터 의심한다.
- **여백 리듬** — A단계에서 수치가 그리드를 지켰어도, 스크린샷에서 리스트 행 간격이 위아래로 다르게 "느껴지면" 실패다(짧은 텍스트 행과 긴 텍스트 행이 섞여 시각적 밀도가 들쭉날쭉해 보이는 경우). 수치 일치와 시각 일치는 별개로 반드시 둘 다 확인한다.
- **정보 밀도** — 한 화면에 스크롤 없이 보이는 항목 수가 실제로 스캔 가능한 양인지(대략 5~8개 항목이 넘어가면서 구분선/그룹핑 없이 나열되면 번잡함 신호). PRD의 실제 사용 규모를 기준으로 그 규모에서도 화면이 안 무너지는지 상상해서 판단한다.
- **클리셰/AI슬롭**(그라데이션 남용, 의미 없는 블롭, 과한 이모지, 동일 카드 반복, **아이콘·이미지 자리표시자 잔존**) — 디자인 시스템 문서가 이미 "그림자는 제품 이미지에만" 같은 원칙을 못박아 뒀다면 그 원칙 위반 자체가 슬롭 신호다.
- **엣지케이스(빈 상태) 완성도** — A단계는 엣지케이스가 "존재하는지"만 확인했다면, C단계는 실제로 "보기에 자연스러운지"를 본다. 긴 텍스트(15자 이상 이름 등)가 줄바꿈되거나 잘리지 않고 레이아웃을 깨지 않는지, 다중 값이 한 줄에 나열될 때 구분자가 읽기 편한지 확인한다.

### C 실패 라우팅 — 재시도 루프

**FAIL을 받으면 다음 절차를 그대로 실행한다. 판단이 끝났다고 멈추지 않는다 — 조치까지 하고 반드시 C를 다시 호출한다.**

1. `codex-critic.sh`(또는 폴백)를 호출한다. `report.md`의 해당 시도 행에 판정 원문을 옮겨 적는다.
2. **PASS면 여기서 루프 종료, [CP4]로 간다.** FAIL이면 3으로.
3. `report.md`의 "재시도 횟수"를 1 늘린다. 단, 진단이 아래 "P단계 범위 예외"에 해당하면 늘리지 않고 곧장 6으로 간다.
4. 아래 표로 진단을 확정하고, 진단에 대응하는 조치를 **지금 이 턴에 바로 실행**한다(다음 세션으로 미루지 않는다).
   - **국소** → 지목된 속성 하나만 고친다. `get_screenshot`으로 그 화면만 재확인한 뒤 1로 돌아간다(같은 시도 세트 안에서 재시도).
   - **방향** → B단계의 해당 축(잠긴 축이 아니라 "열린 축" 절)으로 돌아가 기각했던 후보로 교체하거나 재발산한다. `decisions.md`에 교체 이유와 새 선택을 적은 뒤, G2(마감)까지 다시 실행해 화면을 갱신하고 1로 돌아간다.
   - **반복** → 5로 간다.
5. **재시도 횟수를 확인한다.** 2회에 도달했거나, 직전 시도와 진단 사유가 같으면("반복") 루프를 멈추고 6으로 간다. 아직 상한 전이고 사유도 다르면 4의 조치를 계속한다.
6. **사람에게 에스컬레이션**한다: `report.md` 요약(시도별 판정, 재시도 횟수, 진단 이력)을 보여주고 P/0단계 재정렬이 필요한지 묻는다. 사람이 방향을 정하면 그 지점부터 루프를 다시 1로 시작한다. 사람이 "이대로 간다"고 하면 현재 상태로 [CP4]로 넘어간다 — **이 경우도 반드시 사람이 명시적으로 승인한 것이지, 하네스가 임의로 종료한 게 아니다.**

**무한루프 방지**: 이 루프가 자동으로 도는 것은 4의 "국소"·"방향" 조치 직후 1번(다시 C 호출)뿐이다. 5번(재시도 상한 확인)을 건너뛰고 4를 계속 반복하지 않는다 — 상한 확인은 매 FAIL마다 반드시 거친다.

**P단계 범위 예외** (3에서 언급): 진단이 "PRD 플로우 커버리지 FAIL인데 근거가 P단계에서 의도적으로 뺀 화면"이면, 국소/방향/반복 어디에도 넣지 않고 재시도 카운트도 늘리지 않은 채 곧장 6(사람 에스컬레이션)으로 간다 — Codex는 P단계에서 무엇을 의도적으로 뺐는지 모르므로 이 판단은 항상 메인이 한다.

| 진단 | 조치 |
|---|---|
| 국소 결함 (속성 하나) | 그 속성만 고쳐 C 재검. B로 돌아가지 않는다. 예: 미바인딩 하드코딩 색상, 그리드에서 벗어난 임의 padding, 컨테이너에 남은 기본 흰색 fill이 텍스트를 가리는 경우, 아이콘 자리표시자를 실제 벡터로 교체. **하드 4(상업 퀄리티) FAIL은 거의 항상 이 경로다** — 그림자 강도 불일치, CTA 문구 톤 불일치, 여백 오차처럼 화면 하나하나를 마감하면 해결되는 디테일이기 때문. |
| 방향 오류 (구조 문제) | B로 회귀, 기각 후보로 교체 또는 재발산. 예: 선택한 레이아웃 방식이 실제 데이터 규모에서 구조적으로 안 맞는 경우(그리드가 인원 증가에 못 버팀 등 — B단계 교차 비평에서 근거로 썼어야 할 실패 모드가 실제로 발현된 것). **하드 3(PRD 플로우 커버리지) FAIL이 "화면 자체가 그 유저스토리에 필요한 정보/액션을 담을 구조가 아니다"라는 근거면 이 경로다** — 예: 회신 현황 화면에 애초에 미회신자만 따로 걸러 보는 구조가 없어서 "늦은 회신 독촉" 유저스토리가 완결이 안 되는 경우. |
| 반복 실패 (같은 이유로 2회) | P/0으로 에스컬레이션, CP1 다시. 예: IA를 몇 번 바꿔도 "두 사람이 함께 쓴다"는 조건을 못 살리면, 요구사항 해석 자체를 다시 정렬해야 한다는 신호. |

**주의 — "국소적 결함처럼 보이지만 실은 검증 매체의 한계"인 경우를 구분한다.** 예: 정적 스크린샷에서 필터칩 여러 개가 프레임 폭을 넘어 "잘려 보이는" 경우, 실제로는 가로 스크롤 컨테이너로 정상 동작하는 디자인일 수 있다. 이럴 땐 패딩을 억지로 줄이거나 폰트를 축소해 욱여넣는(=디자인 원칙 위반) "고침"을 하지 말고, 노드 네이밍에 의도(`(scrollable)`)를 남기고 통과 처리한다. 진짜 결함인지 판단하기 전에 "이게 실제 환경(스크롤·인터랙션)에서도 문제인가"를 먼저 따진다. 이 경우 진단은 "해당없음"으로 적고 통과 처리한 뒤 [CP4]로 간다 — 루프를 돌리지 않는다.

## [CP4] 최종 확인

프레젠테이션 페이지 스크린샷 + `report.md` 요약(A단계 게이트 결과, C단계 Codex 판정, 재시도 횟수, 남은 결함)을 보여주고 "됐다"를 받는다. 최종 판단은 항상 사람이 내린다. **CP4 통과 전에는 W단계로 넘어가지 않는다** — 미완성 화면을 배포해 심사자가 먼저 웹 링크로 보게 되는 상황을 막는다.

## W단계 — 웹 배포 (CP4 이후, 선택)

Figma는 심사자가 파일 접근 권한이 있어야 보이고, 인터랙션도 클릭 한 번에 끝난다. **Figma 링크 하나로 부족하고 실제로 눌러볼 수 있는 결과물이 필요할 때** 이 단계를 추가로 실행한다 — 정식 산출물 3종(Figma·brief·decisions·report)을 대체하지 않고 보충한다.

1. **화면 이식**: CP4에서 확정된 최종 화면(1차 범위 전체, G2에서 정리된 최신 상태)을 각각 HTML/CSS로 옮긴다. Figma 변수 컬렉션의 색상 hex 값을 CSS 커스텀 프로퍼티로 그대로 매핑하고(`--color-action-primary: #a85539;` 등), 폰트는 F2에서 정한 한글 대체 폰트(Noto Sans KR 등)를 Google Fonts로 로드한다. 레이아웃 아키타입(리스트 셀 구조, 필탭, 하단 네비)도 Figma 화면의 구조를 그대로 반영한다 — 새로 디자인하지 않는다. **이 단계는 "다시 만들기"가 아니라 "매체 이식"이다.**
2. 화면 간 이동(탭 전환, 뒤로가기)은 최소한의 JS로 구현해 실제로 클릭해볼 수 있게 한다. 데이터는 G단계에서 쓴 것과 같은 목데이터를 그대로 쓴다 — 새 데이터를 지어내지 않는다.
3. `artifact-design` 스킬을 로드한 뒤 Artifact로 publish한다. 여러 화면이 있으면 한 파일 안에서 탭/화면 전환으로 다 보이게 하거나(권장 — 링크 하나로 전체 플로우 확인 가능), 화면별로 나누되 상호 링크를 건다.
4. Publish된 URL을 `report.md`와 (있으면) `SUBMISSION.md`에 "웹 데모"로 기록한다. Figma URL과 나란히 적어 심사자가 원하는 쪽을 고르게 한다.

**이 단계에서 하지 않는 것**: Figma에 없던 새 화면·기능을 웹 버전에서만 추가하지 않는다(두 산출물이 갈라지면 "무엇이 진짜 디자인이냐"는 혼란을 준다). A/C단계 검증은 Figma 화면을 대상으로 이미 끝난 것이므로 웹 버전을 다시 Codex로 검증하지 않는다 — 웹 배포는 검증 대상의 매체 확장이 아니라 열람 편의를 위한 추가 산출물이다.

## 부록 — Figma MCP 작업 시 자주 걸리는 함정

원인 진단용 원칙만 여기 둔다. 그대로 복붙할 코드는 `references/figma-snippets.md`.

- **`figma.createAutoLayout()`의 기본 흰색 fill**: 새로 만든 auto-layout 프레임은 opacity 1의 불투명 흰색 fill을 기본으로 갖는다. 텍스트를 감싸는 투명 컨테이너(탭 아이템, 섹션 래퍼 등)로 쓸 때 이걸 지우는 걸 잊으면, 같은 색 배경 위에서는 안 보이다가 다른 색 배경(예: 검은 탭바) 위에서는 흰 배경이 텍스트를 통째로 가려버린다. 텍스트가 "분명히 만들었는데 스크린샷에 안 보인다"면 제일 먼저 부모 컨테이너의 `fills`부터 확인한다.
- **한글 텍스트에 라틴 전용 폰트만 로드하면 렌더가 비게 된다**: 패턴/문서가 "SF Pro → Inter 대체"라고만 명시했어도, 실제 콘텐츠가 한글이면 그 폰트의 한글 글리프 지원 여부를 먼저 확인해야 한다. Inter·Manrope 등 대부분의 서구 산세리프는 한글이 없다 — `Noto Sans KR` 등으로 전환한다.
- **`layoutSizingHorizontal = 'FILL'`은 `appendChild` 이후에만 설정 가능**: 자식 노드를 만들자마자 FILL을 설정하면 에러가 난다. 부모에 먼저 붙이고 그다음 sizing을 설정하는 순서를 지킨다.
- **가로로 넘치는 콘텐츠를 억지로 줄여서 우겨넣지 않는다**: 필터칩 같은 요소가 프레임 폭을 넘으면, 디자인 원칙을 깨면서까지 욱여넣기보다 가로 스크롤 컨테이너라는 걸 인정하고 넘어간다(C단계 라우팅 참고).
- **`Presentation` 페이지의 클론은 라이브 링크가 아니다**: 컴포넌트를 G2에서 나중에 고쳐도 Presentation의 클론에는 반영 안 된다. 최종 마감 후 마지막으로 한 번 재클론한다.
- **컴포넌트 레벨 수정으로 안 잡히는 화면 전용 도형**: 화면에 공용 컴포넌트 밖에서 직접 그린 요소(예: 홈 화면 헤더에만 별도로 얹은 아이콘)는 Library 컴포넌트를 고쳐도 자동 반영되지 않는다. A/C단계 재검 시 화면별로 한 번 더 검색한다.
