# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP(`use_figma`)로 **작업장에 실제 화면을 생성**하는 하네스.
방향은 **기획 → Figma 생성**이다. Figma → 코드가 아니다.

이 파일은 각 단계가 **무엇을 판단해야 하는지**의 기준 원본이다. 실행 순서·게이트·파일 핸드오프는 `CLAUDE.md`가, 각 단계의 구체 절차는 `.claude/agents/0N-*.md`가 갖는다. 세 문서가 충돌하면 우선순위는 `design.md` 본문 > `CLAUDE.md` > 이 파일 > 에이전트 파일이다.

## 파일 지도

순서를 그대로 따라가는 것이 아니라, 아래 단계가 각각 무엇을 판단해야 하는지에 집중한다.

| ------------------------ | -------- | ------------------------------------------------ | ----------------------------------------------- | ------------------------------- |

| B-1 IA 발산·수렴         | 01       | `work/brief.md`                                  | `work/ia.md`, `work/decisions.md` Part 1        | **게이트 1** (최상위 구조 선택) |

게이트 형식은 `CLAUDE.md`의 A/B/C 선택형만 쓴다. 자유서술을 요구하지 않는다. 사용자가 "auto"라고 하면 추천안(A)을 자동 선택하고 `work/decisions.md`에 "자동 선택"으로 기록한다.

## 판단기준 3계층 (어디서 정해지는가)

| 계층                        | 이 하네스에서                                                                                                         |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 완전 고정 (프로젝트 무관)   | 터치 타깃 ≥ 44px, 자동 레이어명 0개, 미바인딩 fill 0개, 그라디언트·이모지·카드 그림자 금지                            |
| 항목 고정 · 값은 프로젝트별 | A/C 체크 카테고리는 아래 표로 고정. 기준값(팔레트·타이포·간격·컴포넌트 키)은 `design.md` 부록 A와 `work/brief.md`에서 |
| 완전 프로젝트별             | PRD §3 까다로운 상황 6개의 화면 매핑, 목데이터 엣지케이스 8종, 도메인 문구("아직 모임이 없어요")                      |

에이전트가 결정해도 되는 것 / 안 되는 것의 경계는 `design.md` 부록 C 표가 유일한 기준이다. 표 밖의 결정은 하지 않고 사람에게 보고한다.

## 0단계 — 요구사항 정렬 (01-planner)

화면을 만들기 전, 무엇을 만들어야 하는지 자체가 불확실할 때 실행한다.

- **레퍼런스/시나리오 소싱 방법**: 스크린샷 레퍼런스 대신 **구체 시나리오 내러티브 3개**를 쓴다("결혼식 10주 전 토요일 아침, 예비신부가 앱을 켰다…"). 각 시나리오는 PRD §3의 까다로운 상황(중복 소속 / 늦은 회신 / 겹치는 모임 / 1:1 / 상견례 / 급한 모임) 중 최소 2개를 품는다. 이유: 이 하네스의 시각 언어는 `design.md`로 이미 고정돼 있어, 0단계에서 뽑아야 할 것은 무드가 아니라 **흐름과 우선순위**다.
- **질문 형식**: 라벨형 질문 금지. 시나리오를 보여주고 "이 흐름이 자연스러운가, 어디가 어색한가"를 자유서술로 받는다. IA/플로우는 다이어그램이 아니라 시나리오로 체험시킨다. 사람이 없거나 auto 모드면 "반응 미수집"으로 표시하고 진행한다.
- **판단기준 역추출 방법**: PRD 문장 → "이 서비스는 ~~해야 한다" 5~~8개. 각 항목에 근거 문장 인용. 예시:
  - "방이 수십 개로 늘어나면 놓친다" → 조망이 상세보다 상위. 첫 화면은 전체 상태 요약.
  - "며칠씩 답이 없는 사람이 꼭 있다" → 미회신자는 숨기지 않고 마감까지 남은 시간과 함께 노출.
- **가정 처리**: 확정 안 된 정보는 가정 로그에 "이렇게 가정했습니다 + 근거"로 명시. 침묵 처리 금지. 최소 항목: 플랫폼(모바일 고정), 주 사용자 계정 구조, 지인 진입 방식(앱/링크), 알림 채널, 로그인 유무, 장소 정보 포함 여부.
- **자족성**: `work/brief.md`에 부록 A 토큰 값을 그대로 옮겨 적는다. 04-reviewer가 브리프만 보고도 검사할 수 있어야 한다.
- **산출물**: `work/brief.md` (템플릿: `templates/brief.md`)

## B단계 — 발산·수렴 (01-planner: IA / 02-wireframer: 화면 구성)

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: 후보를 만들기 전에 축을 분리한다. 축을 나누지 않고 화면 전체를 통째로 비교하면 무엇 때문에 선택했는지 뒤섞여(confound) 근거가 안 남는다.
  - IA 축(01): ① 최상위 구조(사람/모임/일정 중 무엇을 탭으로) ② 두 사용자 분리 방식(토글/필터/별도 화면) ③ 초대받은 지인 경험(앱 내/링크). 프로젝트마다 다시 생각한다.
  - 화면 구성 축(02): 밀도(요약 vs 상세), 위계(무엇을 첫 스크롤에).
- **후보 생성 방식**: 축마다 2~3개 병렬.
- **비교·수렴 방식**: 두 관점 교차 비평 — **UX 관점**(까다로운 상황 6개를 몇 번 탭으로 해결하는가) / **일관성·구현 관점**(`design.md` 부록 A 컴포넌트만으로 되는가, 화면 수 증가). 추천 1개 + 이유, 나머지는 탈락 이유 1줄. 최종 선택은 게이트에서 사람이.
- **IA 산출 기준(01)**: 탭 3~5개. **P0 화면 6~9개** — 지인 풀 → 모임 편성 → 일정 후보 → 회신 수합 → 확정 → 전체 조망이 끊기지 않게. 까다로운 상황 6개가 **어느 화면의 어느 요소**에서 다뤄지는지 매핑 표 필수(PRD 평가 기준).
- **와이어프레임 산출 기준(02)**: 03이 해석 없이 조립할 수 있어야 한다. 모든 블록에 컴포넌트 키(`design.md` §Components 또는 부록 A-4에 있는 것만, 없으면 "조합: X + Y")·목데이터 경로·상태를 적는다. "적당한 텍스트" 금지. 픽셀값 직접 쓰지 않고 토큰 키로만. 탭 가능한 요소는 목적지 화면이 있어야 한다.
- **목데이터 기준(02)**: `design.md` 부록 B 8개 규칙 전부. `edgeCases` 8개 키(multiGroupPerson / lateReplier / overlappingMeetings / oneOnOne / bothSides / urgent / emptyGroup / longText)가 전부 채워져야 한다. 못 채우면 이유를 적고 멈춘다.
- **산출물**: `work/decisions.md` (템플릿: `templates/decisions.md`, 01이 Part 1 작성 → 02가 Part 2 이어쓰기), `work/ia.md`, `work/wireframes/_index.md` + `{screen-id}.md`, `work/mock-data.json`

## 빌드 — 조립 규칙 (03-figma-builder)

자유 창작을 하지 않는다. `design.md`가 시각 언어를, 와이어프레임이 구조를 이미 정했다. 03은 그것을 **정확히 조립**한다. 아래는 A단계에서 걸릴 것을 빌드 시점에 막는 규칙이다.

- **Foundations 선행**: 화면은 변수(컬렉션 `design.md`)·텍스트 스타일(`typography/*`)·이펙트 스타일(`effect/product-shadow` 1개)·컴포넌트(부록 A-4 + 버튼 5종)를 참조만 한다. 부록 A-4의 `status-bar`(Apple iOS 표준, theme light/dark)는 Foundations 필수 컴포넌트이며 `mobile-header` safe-top에 내장돼 있다. 헤더 없는 프레임만 standalone 인스턴스를 레이어 최상단에 놓는다. hex/픽셀 직접 입력 금지. 변수가 없는 alpha 값(hairline 0.08, chip 0.64, parchment 0.8)은 변수 색 + opacity로.
- **폰트**: SF Pro 없으면 Inter 대체(`design.md` §Note on Font Substitutes). weight 300/400/600/700만. **500 금지.**
- **1호출 1화면**: Foundations는 별도 호출. 화면은 호출당 1개. 상태 프레임(`{id}--empty` 등)은 같은 호출에서 오른쪽에.
- **레이어 네이밍**: `{screen-id} / {블록} / {요소}`. 자동 이름 남기지 않는다.
- **소유권**: 이번 실행에서 만든 노드 외에는 수정·삭제하지 않는다. `FIX-LOCAL`이면 리뷰 파일의 수정 목록 항목만 국소 수정, 그 외는 같은 이름 노드를 지우고 재생성.
- **상태바 필수** (design.md A-1-1): 모든 화면 프레임(상태 프레임 포함)의 첫 자식은 `status-bar` 인스턴스(`x 0 / y 0`, 390×47). 와이어에 없어도 넣는다. 직접 그리지 않는다.
- **자체 검증** (리뷰어 가기 전 1회): 자동 이름 0개 / 미바인딩 솔리드 fill 0개 / 텍스트 스타일 미적용 0개 / 프레임마다 `status-bar` 인스턴스 합산 정확히 1개(헤더 내장 포함)·가시. 위반은 스스로 고친다.
- **로그**: `work/figma-log.md`에 노드 ID·컴포넌트 키·자체 검증 결과·스크린샷 경로 append. `_index.md` 상태를 `built`로.
- **오류**: 같은 단계 3회 실패 → 자기 노드 삭제 → "MCP 오류 3회" 보고 후 종료. 임의 우회 금지.

## C단계 — 미적·게슈탈트 판단 (04-reviewer)

화면이 다 만들어진 뒤, 반드시 `get_screenshot`으로 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가. 각 항목에 **관찰 → 기준(`design.md` 어느 문장) → 판정**을 쓴다. 근거 없는 항목은 "관찰만, 판정 보류".

| #   | 항목                       | 이 프로젝트의 판단 기준                                                                                                                                                                                                                                                                                                                       |
| --- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1  | 섹션 간 색온도·조명 일관성 | 표면은 white / parchment / near-black 셋뿐. 다른 톤(회색 카드 배경, 파스텔)이 보이면 실패. dark 섹션은 화면당 1개 이하 — 두 개면 "타일 리듬"이 아니라 "패널"로 읽혀 Apple 언어가 깨진다.                                                                                                                                                      |
| C2  | 시각적 위계                | 3초 안에 가장 중요한 것이 **하나**로 읽혀야 한다. display-md 제목은 화면당 1개. 파란 pill CTA는 1~2개(3개부터 "무엇을 누르라는 건지" 흐려짐). 헤더 우측 CTA와 하단 sticky CTA가 같은 행동이면 실패.                                                                                                                                           |
| C3  | 여백 리듬의 체감 일관성    | 수치가 맞아도 위쪽이 아래보다 빽빽하면 실패. 섹션 간 간격이 시각적으로 같은 급으로 느껴져야 한다. 내용이 24px 마진을 침범하면 실패.                                                                                                                                                                                                           |
| C4  | 정보 밀도                  | 리스트 행은 제목 + 메타 2줄까지. 한 행에 chip 2개 초과 금지. 숫자 요약은 화면당 4개 이하 — "숫자 요약"은 요약 행·다크 바·카운트다운처럼 **독립 통계 요소**를 말하며, 섹션 헤더의 건수 캡션("회신 대기 3")이나 리스트 행 메타의 숫자는 세지 않는다. "한 번에 다 보여주자"는 이 언어에서 항상 틀린 답이다 — 조망은 숫자 요약, 상세는 다음 화면. |
| C5  | 클리셰/AI슬롭              | 하나라도 있으면 실패: 색으로 상태 구분한 chip(초록=확정 등), 카드 그림자, 그라디언트, 이모지 아이콘, 보라·인디고 계열, 카드 안의 카드, 의미 없는 일러스트, 좌우 꽉 채운 큰 파란 버튼 2개 연속.                                                                                                                                                |
| C6  | 엣지케이스 실제 완성도     | `--empty`가 default와 같은 헤더를 갖는가(존재는 A7, 품질은 여기). 문구가 도메인 맥락인가("데이터가 없습니다" 실패, "아직 모임이 없어요. 첫 모임을 만들어 보세요" 합격). 긴 이름(15자+)이 잘리거나 겹치는가.                                                                                                                                   |

## 판정과 라우팅 (04-reviewer → 오케스트레이터)

C단계는 합격/불합격이 아니라 **원인 진단**까지 낸다. 원인의 층위에 따라 분기한다.

| 판정         | 조건                                                                          | 다음 행동                                                                      |
| ------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `PASS`       | A1~~A11, C1~~C6 전부 통과                                                     | `_index.md` → `reviewed-pass`. 다음 화면                                       |
| `FIX-LOCAL`  | A 항목 실패(전부) 또는 C 실패가 **속성 하나**(간격·문구·chip)로 고쳐지는 경우 | 03에게 노드 ID + 수정 목록. 같은 화면 국소 수정 후 재검. B로 돌아가지 않음     |
| `REDIRECT-B` | 블록 구성·순서·개수 문제 — 국소 조정으로 안 고쳐지는 구조 문제                | 02에게 **축 언어**(밀도 축 / 위계 축)로 사유 전달. 해당 화면만 재발산 → 게이트 |
| `ESCALATE-0` | 같은 이유로 `REDIRECT-B`가 이미 1회 있었음 (요구사항 해석 문제)               | 사람에게 보고. 01 재실행 여부는 사람이 결정                                    |

- **재시도 상한**: 같은 화면 `FIX-LOCAL` 3회 → `REDIRECT-B` 승격. `REDIRECT-B` 2회 → `ESCALATE-0`. 회차는 이전 `work/reviews/{id}.md`에서 센다.
- **사람을 부르는 경우는 셋뿐**: 게이트 1~3, `ESCALATE-0`, Figma MCP 오류 3회 연속. 그 외에는 부르지 않는다.
- 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.
- 04는 노드를 수정하지 않는다(읽기 전용). A 검사를 스크린샷으로, C 검사를 노드 속성으로 대체하지 않는다.
