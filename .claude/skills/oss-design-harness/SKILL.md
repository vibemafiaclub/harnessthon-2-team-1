# oss-design-harness

현업 디자이너의 판단 기준을 추출해, Figma MCP(`use_figma`)로 **작업장에 실제 화면을 생성**하는 하네스.
실행은 `.claude/agents/01-planner → 02-wireframer → 03-figma-builder → 04-reviewer`가 하고, 이 파일은 각 단계가 **무엇을 판단해야 하는지**의 기준 원본이다. 기준값은 `design.md`(Apple 웹 디자인 언어 + 모바일 부록)와 `work/brief.md`에서 캘리브레이션된다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중한다.

## 0단계 — 요구사항 정렬 (01-planner)

화면을 만들기 전, 무엇을 만들어야 하는지 자체가 불확실할 때 실행한다.

- **레퍼런스/시나리오 소싱 방법**: 스크린샷 레퍼런스 대신 **구체 시나리오 내러티브 3개**를 쓴다("결혼식 10주 전 토요일 아침, 예비신부가 앱을 켰다…"). 각 시나리오는 PRD의 까다로운 상황을 최소 2개 품는다. 이유: 이 하네스의 시각 언어는 design.md로 이미 고정돼 있어, 0단계에서 뽑아야 할 것은 무드가 아니라 **흐름과 우선순위**다.
- **질문 형식**: 라벨형 질문 금지. 시나리오를 보여주고 "이 흐름이 자연스러운가, 어디가 어색한가"를 자유서술로 받는다. IA/플로우는 다이어그램이 아니라 시나리오로 체험시킨다.
- **판단기준 역추출 방법**: PRD 문장 → "이 서비스는 ~해야 한다" 변환. 예시:
  - "방이 수십 개로 늘어나면 놓친다" → 조망이 상세보다 상위. 첫 화면은 전체 상태 요약.
  - "며칠씩 답이 없는 사람이 꼭 있다" → 미회신자는 숨기지 않고 마감까지 남은 시간과 함께 노출.
- **가정 처리**: 확정 안 된 정보는 `work/brief.md` 가정 로그에 "이렇게 가정했습니다 + 근거"로 명시. 침묵 처리 금지.
- **산출물**: `work/brief.md` (템플릿: `templates/brief.md`)

## B단계 — 발산·수렴 (01-planner: IA / 02-wireframer: 화면 구성)

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: 후보를 만들기 전에 축을 분리한다. 이 도메인의 IA 축: ① 최상위 구조(사람/모임/일정 중 무엇을 탭으로) ② 두 사용자 분리 방식(토글/필터/별도 화면) ③ 초대받은 지인 경험(앱 내/링크). 화면 구성 축: 밀도(요약 vs 상세), 위계(무엇을 첫 스크롤에).
- **후보 생성 방식**: 축마다 2~3개 병렬. 화면 전체를 통째로 비교하지 않는다.
- **비교·수렴 방식**: 두 관점 교차 비평 — **UX 관점**(까다로운 상황 6개를 몇 번 탭으로 해결하는가) / **일관성·구현 관점**(design.md 부록 A 컴포넌트만으로 되는가, 화면 수 증가). 추천 1개 + 이유, 나머지는 탈락 이유 1줄. 최종 선택은 게이트에서 사람이.
- **산출물**: `work/decisions.md` (템플릿: `templates/decisions.md`)

## A단계 — 구조적 사실 검증 (04-reviewer)

화면이 다 만들어진 뒤, 데이터로 예/아니오 또는 수치로 검증한다. 스크린샷 없이 Figma 노드 속성만으로 확인 가능.

체크 카테고리 (항목은 고정, 기준값은 design.md에서):

- [x] 컬러 팔레트 일관성 — 솔리드 fill/stroke는 전부 컬렉션 `design.md` 변수 바인딩. 허용 팔레트: design.md §Colors 19개 + alpha 변형(hairline 0.08, chip 0.64, parchment 0.8). 미바인딩 0개.
- [x] 타이포 스타일 재사용 — 텍스트 노드 전부 `typography/*` 스타일 적용. weight 500 사용 0개. 모바일에서 hero-display/display-lg/lead 사용 0개.
- [x] Spacing 그리드 준수 — 단위 8px. 허용값 4/8/12/17/24/32/48/80 (텍스트 미세조정 2·5·6·7 허용). 좌우 마진 24.
- [x] 컴포넌트 재사용률 — 인스턴스 ÷ (인스턴스 + 프리핸드 프레임) ≥ 0.7.
- [x] 레이어 네이밍 semantic 여부 — `{screen-id} / {블록} / {요소}`. 자동 이름(`Frame N`, `Rectangle N`) 0개.
- [x] Variant 상태 커버리지 — 와이어프레임 `## 상태`에 적힌 상태(empty 필수, selected/error 해당 시)마다 프레임 존재.
- [x] 터치 타깃 — 탭 가능 컴포넌트 높이 ≥ 44 (chip 32 허용).
- [x] 그림자 — `effect/product-shadow` 외 이펙트 0개.

## C단계 — 미적·게슈탈트 판단 (04-reviewer)

화면이 다 만들어진 뒤, 반드시 `get_screenshot`으로 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

체크 항목과 이 프로젝트의 판단 기준:

- [x] 섹션 간 색온도·조명 일관성 — 표면은 white / parchment / near-black 셋뿐. 다른 톤(예: 회색 카드 배경, 파스텔)이 보이면 실패. dark 섹션은 화면당 1개 이하 — 두 개면 "타일 리듬"이 아니라 "패널"로 읽혀 Apple 언어가 깨진다.
- [x] 시각적 위계가 한눈에 읽히는가 — 3초 안에 가장 중요한 것이 **하나**로 읽혀야 한다. display-md 제목은 화면당 1개. 파란 pill CTA는 1~2개(3개부터 "무엇을 누르라는 건지" 흐려짐). 헤더 우측 CTA와 하단 sticky CTA가 같은 행동이면 실패.
- [x] 여백 리듬의 체감 일관성 — 수치가 맞아도 위쪽이 아래보다 빽빽하면 실패. 섹션 간 간격이 시각적으로 같은 급으로 느껴져야 한다. 내용이 24px 마진을 침범하면 실패.
- [x] 정보 밀도 번잡함 여부 — 리스트 행은 제목 + 메타 2줄까지. 한 행에 chip 2개 초과 금지. 숫자 요약은 화면당 4개 이하. "한 번에 다 보여주자"는 이 언어에서 항상 틀린 답이다 — 조망은 숫자 요약, 상세는 다음 화면.
- [x] 클리셰/AI슬롭 여부 — 다음 중 하나라도 있으면 실패: 색으로 상태 구분한 chip(초록=확정 등), 카드 그림자, 그라디언트, 이모지 아이콘, 보라·인디고 계열, 카드 안의 카드, 의미 없는 일러스트, 좌우 꽉 채운 큰 파란 버튼 2개 연속.
- [x] 엣지케이스(빈 상태 등)의 실제 완성도 — `--empty`가 default와 같은 헤더를 갖는가(존재는 A, 품질은 여기). 문구가 도메인 맥락인가("데이터가 없습니다" 실패, "아직 모임이 없어요. 첫 모임을 만들어 보세요" 합격). 긴 이름(15자+)이 잘리거나 겹치는가.

### C단계 실패 시 라우팅

원인을 진단해서 아래 셋 중 하나로 분기한다.

1. **국소적 결함** (표면 속성 하나의 문제) → `FIX-LOCAL`: 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다.
2. **방향 자체가 틀림** (블록 구성·순서·개수 — 국소 조정으로 안 고쳐지는 구조적 문제) → `REDIRECT-B`: 02-wireframer에게 축 언어(밀도/위계)로 사유를 넘겨 해당 화면만 재발산.
3. **반복 실패** (REDIRECT-B 후에도 같은 이유로 탈락) → `ESCALATE-0`: 요구사항 해석 문제. 사람에게 보고, 01-planner 재실행 여부는 사람이 결정.

재시도 상한: 같은 화면 `FIX-LOCAL` 3회 → `REDIRECT-B` 승격. `REDIRECT-B` 2회 → `ESCALATE-0`. 상한 초과 시 사람에게 에스컬레이션. 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.
