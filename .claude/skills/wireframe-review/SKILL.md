# wireframe-review

`wireframe` 스킬이 남긴 실행 폴더 하나를 받아 [docs/MVP_와이어프레임_설계_체크리스트.md](../../../docs/MVP_와이어프레임_설계_체크리스트.md)의 11개 항목과 최종 체크 10개에 대조한다. 결과는 항목별 판정과 개선 항목 목록이다. 개선 항목은 다음 `wireframe` 실행의 입력이 된다.

이 스킬은 평가만 한다. spec.md나 wireframe.md을 고치지 않는다. 고치는 일은 개선 항목을 받은 `wireframe` 스킬이 한다.

## 입력 확인

| 항목 | 없을 때 |
| --- | --- |
| 실행 폴더 경로 (`wireframes/output/<YYYYMMDD>-<slug>/`) | 사용자에게 묻는다. 없으면 `wireframes/output/README.md` 인덱스의 마지막 줄을 기본값으로 쓰고 그렇게 했다고 말한다 |
| 폴더 안의 `spec.md`, `components.md`, `wireframe.md`, `README.md` | 하나라도 없으면 진행하지 않고 어떤 파일이 없는지 보고한다. wireframe.md가 없으면 레이아웃 관련 항목을 평가할 수 없다 |
| 체크리스트 문서 | 기본값은 `docs/MVP_와이어프레임_설계_체크리스트.md`. 사용자가 다른 문서를 주면 그것을 쓴다 |
| 입력 문서 (`wireframes/input/`) | PRD, User Flow, IA, 제약사항. "PRD에 없는 기능이 들어갔는가", "필수 요구사항이 빠졌는가"를 판단하려면 필요하다. 없으면 그 항목을 "판단 불가"로 둔다 |
| 이전 평가 (`review.md`) | 같은 폴더나 이전 실행 폴더에 있으면 읽는다. 이미 지적한 항목이 고쳐졌는지 확인한다 |

## 작업 순서

### 1단계. 산출물 읽기

spec.md, components.md, wireframe.md, README.md를 전부 읽는다. 입력 폴더의 PRD와 IA도 읽는다. 읽기 전에 판정하지 않는다.

읽으면서 아래를 메모한다. 뒤 단계에서 근거로 쓴다.

- 그린 화면과 State 목록
- 가정 로그에 올라간 항목
- 5단계 검수표에서 "아니오"나 "부분"으로 남긴 항목
- Component Inventory의 개수와 화면 수

### 2단계. 항목별 판정

체크리스트 1~11장을 차례로 본다. 장마다 아래 넷 중 하나로 판정하고 근거를 한 문장으로 적는다. 근거에는 파일과 위치(spec.md의 절 이름, wireframe.md의 프레임 이름)를 넣는다.

| 판정 | 기준 |
| --- | --- |
| 통과 | 장 안의 질문 전부에 "예"라고 답할 수 있다 |
| 부분 | 일부만 충족. 무엇이 빠졌는지 적는다 |
| 미달 | 장이 요구하는 것이 없다. 특히 8장(최소 상태)의 "필요" 조건에 해당하는 State가 빠지면 미달이다 |
| 해당 없음 | 이 실행 범위에서 평가할 수 없다. 이유를 적는다. 예: 입력 화면을 안 그렸으면 9장 입력과 결과 |

판정할 때 지키는 것:

- 체크리스트의 질문에만 답한다. 취향이나 시각적 완성도는 이 스킬의 범위 밖이다.
- "화면 하나만 그렸다"는 사실을 미달 사유로 쓰지 않는다. 그린 범위 안에서 판정한다. 범위 밖 항목은 해당 없음이다.
- 가정 로그에 올라간 항목은 미달로 세지 않는다. 대신 "확인 필요"로 개선 항목에 옮긴다.
- 8장 최소 상태는 표의 "설계 필요 기준"을 그대로 적용한다. Success는 핵심 행동의 완료 결과가 있으면, Error는 실패 시 진행할 수 없으면 필요하다.
- 3장 기능 범위는 PRD의 우선순위와 대조한다. PRD가 필수로 둔 기능이 Later나 Remove면 부분으로 판정하고 개선 항목에 올린다.

최종 체크 10개도 같은 네 판정으로 표를 만든다.

### 3단계. 개선 항목 도출

부분·미달 판정마다 개선 항목을 하나 이상 만든다. [templates/review.md](templates/review.md)의 개선 항목 표 양식을 쓴다.

| 열 | 적는 것 |
| --- | --- |
| 번호 | R-01부터 |
| 체크리스트 항목 | 장 번호와 이름 |
| 문제 | 무엇이 어떻게 부족한지 한 문장 |
| 조치 | `wireframe` 스킬이 다음 실행에서 할 일. 화면·State·Component 단위로 구체적으로 |
| 우선순위 | 필수 / 권장 / 확인 필요 |
| 영향 | 바뀌는 파일과 프레임 |

우선순위 기준:

- **필수**: 체크리스트가 "반드시" 또는 "필요"라고 한 것. 8장의 State, 5장의 Primary CTA, 6장의 핵심 플로우 완결.
- **권장**: 없어도 플로우는 돌지만 데모나 다음 디자인 단계에서 문제가 되는 것. 7장 CTA 가시성, 11장 데모 더미 데이터.
- **확인 필요**: 고치려면 PRD, User Flow, IA를 바꿔야 하는 것. 조치에 "상위기획 확인"을 적고 스킬이 임의로 고치지 않도록 표시한다.

개선 항목을 만들 때 지키는 것:

- PRD에 없는 기능을 조치로 제안하지 않는다. 필요해 보이면 "확인 필요"로 올린다.
- 조치는 하나의 실행에서 끝낼 수 있는 크기로 쓴다. "전체 화면을 다시 그린다"는 조치가 아니다.
- 같은 원인에서 나온 문제는 항목 하나로 합친다.
- 이전 review.md가 있으면 그때 지적한 항목 중 안 고쳐진 것을 앞에 두고 "재지적"으로 표시한다.

### 4단계. 저장

1. 평가 대상 실행 폴더 안에 `review.md`를 쓴다. 양식은 [templates/review.md](templates/review.md)다. 같은 폴더에 review.md가 이미 있으면 `review-2.md`처럼 번호를 붙인다.
2. 실행 폴더의 `README.md` 맨 아래에 `## 평가` 절을 붙이고 review.md 링크, 판정 요약(통과 n · 부분 n · 미달 n · 해당 없음 n), 필수 개선 항목 수를 적는다.
3. `wireframes/output/README.md` 인덱스의 해당 줄 비고 열에 "평가: 필수 n건"을 덧붙인다.
4. 커밋은 사용자가 요청할 때만 한다. 메시지는 `docs(wireframe): <slug> 평가` 형식이다.

### 5단계. 다음 실행 안내

보고 맨 끝에 다음 `wireframe` 실행을 위한 한 줄을 적는다.

```
/wireframe wireframes/input/ 을 입력으로, wireframes/output/<실행 폴더>/review.md 의 개선 항목을 반영해 다시 실행해줘. slug는 <slug>-improved.
```

필수 항목이 0건이면 재실행을 권하지 않고 "다음 범위로 넘어가도 된다"고 적는다.

## 산출물

```
wireframes/output/<YYYYMMDD>-<slug>/
  review.md        # 항목별 판정 + 최종 체크 + 개선 항목
  README.md        # 맨 아래 "## 평가" 절 추가
```

## 하지 않는 것

- spec.md, components.md, wireframe.md을 고치지 않는다. 평가만 한다.
- 체크리스트에 없는 기준으로 지적하지 않는다. 색, 서체, 여백 취향은 범위 밖이다.
- PRD에 없는 기능을 개선 조치로 넣지 않는다.
- 그린 범위 밖의 화면이 없다는 이유로 미달을 주지 않는다.
- 가정 로그에 이미 있는 항목을 미달로 다시 세지 않는다.

## 관련 스킬

- `wireframe`: 평가 대상을 만들고, 이 스킬의 개선 항목을 받아 다시 실행한다.
