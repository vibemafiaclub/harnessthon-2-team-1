# Brief — 청첩장모임 스케줄러

## 입력 조건

- PRD: `docs/청첩장모임-스케줄러-PRD.md` (Greenfield, 화면/레이아웃 미지정)
- 디자인 시스템: `docs/design.md` (Apple 웹 디자인 언어 → 모바일 앱 적용본, 사람이 확정한 토큰·컴포넌트·목데이터 규칙)

**이번 프로젝트의 0단계는 표준 하네스와 다르게 좁혀진다.** design.md가 이미 색·타이포·spacing·컴포넌트 토큰을 전부 확정해서 준 상태라, "디자인 토큰 추출"은 0단계에서 할 일이 아니다. design.md 부록C가 명시적으로 "IA 구조(탭 개수·이름)는 사람 게이트"라고 선을 그어놓았으므로, 0단계가 실제로 정렬해야 하는 것은 **PRD 기능요구사항을 어떤 화면·탭 구조로 매핑할지**로 좁혀진다.

## 보여준 레퍼런스 / 자극

- 레퍼런스 1: Doodle/When2meet 스타일 그리드 히트맵 vs 카카오톡 단체채팅 스타일 O/X 응답 로우파이 프로토타입 (Artifact로 실제 클릭 가능하게 구현) — 일정조율 UX의 두 방향을 체험시키기 위함.
- 레퍼런스 2: PRD §3 "사용자들의 상황" 자체가 이미 자유서술형 시나리오 — 청첩장 40~100명, 주말 2~3건, 1:1 모임, 늦은 회신, 양가 모임, 임박 모임 등 엣지케이스가 원문에 이미 내러티브로 존재.

## 역추출한 암묵적 판단기준

- **탭 구조**: "지인풀 등록·관리 / 모임 편성 / 일정 후보·회신 / 확정 / 전체 조망 / 상태 구분" 6개 기능요구사항 중, 확정·일정후보는 모임의 하위 상태이지 별도 화면이 아니라고 판단 → **모임 상세 안으로 흡수**. 전체조망+상태구분은 하나의 "오늘 상황판" 개념으로 묶임 → **홈 탭**. 결과: 3탭(홈/모임/지인풀)으로 수렴.
  - 근거: PRD 조건 "예비신랑·예비신부 두 사람이 함께 쓰는 것"을 고려하면 탭이 많아질수록 두 사람이 서로 다른 탭에 머무르며 놓치는 정보가 늘어난다 → 탭 최소화가 "전체조망" 요구사항과 정합적.
- **회신 현황 UI**: 그리드 히트맵(Doodle 스타일)이 한눈에 겹치는 날짜를 보여주는 데는 유리하지만, design.md가 지정한 모바일 프레임(390px)에서 참석자가 5~6명을 넘으면 가로스크롤이 발생해 design.md의 "가로스크롤 지양" 원칙과 충돌. → **list-row + status-chip 조합**(design.md 기존 컴포넌트 재사용, 부록C상 "결정 가능" 범위)으로 세로 스크롤형으로 대체.
  - 근거: PRD §3 "모임당 3~6명"이 표준 규모이므로, 5명 초과 구간에서도 안정적인 레이아웃이 그리드보다 리스트.

## 명시적 가정 로그

- PRD가 화면 개수·흐름을 지정하지 않았으므로, 위 3탭 IA는 이번 세션에서 사람이 직접 선택(AskUserQuestion)해 확정한 것 — "가정"이 아니라 "명시적 결정"으로 기록.
- 모임 생성 플로우(멤버 선택 → 날짜 후보 제안 → 마감 설정)는 PRD 기능요구사항 1~3을 순서대로 이었다고 가정. 실제 사용자가 날짜 후보를 먼저 정하고 멤버를 나중에 추가하는 역순 플로우 가능성은 이번 스코프에서 배제.
- "상견례처럼 양가가 같이 나가는 모임"은 별도 화면이 아니라 모임 편성 시 신랑측/신부측 지인을 함께 선택할 수 있게 하는 것으로 처리(그룹 자체를 "양가 공용"으로 만들지 않음).

- 타이포: SF Pro Display/Text → Inter 대체, 모바일은 `{typography.display-md}`(34px) 이하만 사용
- 프레임: 390×844px (부록A)

## IA 확정 (사람 게이트 통과)

3탭: **홈 / 모임 / 지인풀**

| 탭 | 내용 |
|---|---|
| 홈 | 오늘의 일정 + 전체 캘린더 + 상태별(회신대기/확정대기/확정/완료) 그룹핑 |
| 모임 | 내 모임 리스트(상태 필터) + 새 모임 만들기 FAB → 모임 상세(후보제안/회신현황/확정) |
| 지인풀 | 이름·관계·연락처 리스트 + 그룹 필터, 다중 그룹 소속 표시 |
