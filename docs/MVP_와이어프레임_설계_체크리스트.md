# MVP 와이어프레임 설계 시 프로덕트 디자이너가 확인해야 할 요소

MVP 와이어프레임의 목적은 모든 상황을 완성도 높게 설계하는 것이 아니라,
**핵심 사용자 가치가 실제로 작동하는 최소한의 흐름을 빠르게 정의하는
것**입니다. 화면 수와 기능을 늘리기보다, 사용자가 핵심 가치를 경험하는
데 필요한 흐름이 끊기지 않는지를 우선 확인합니다.

## 1. 핵심 사용자와 문제

와이어프레임을 시작하기 전에 다음을 한 문장으로 정의합니다.

-   핵심 사용자는 누구인가?
-   사용자가 해결하려는 문제는 무엇인가?
-   이 제품이 제공하는 핵심 가치는 무엇인가?

화면이나 기능이 이 문제 해결과 직접 관련이 없다면 MVP 범위에서 제외하는
것을 우선 검토합니다.

## 2. 핵심 경험 정의

사용자가 제품의 가치를 가장 명확하게 경험하는 순간을 먼저 정의합니다.

예시 흐름:

`문제 상황 진입 → 핵심 정보 입력 → 제품의 핵심 처리 → 결과 확인 → 다음 행동`

와이어프레임은 이 핵심 경험을 중심으로 구성합니다.

-   사용자가 어떤 순간에 제품의 가치를 이해하는가?
-   그 경험까지 반드시 필요한 단계는 무엇인가?
-   제거해도 핵심 경험이 유지되는 단계는 무엇인가?

## 3. MVP 기능 범위

기능은 다음 기준으로 구분합니다.

  구분      기준
  --------- ----------------------------------------------
  Core      핵심 가치를 경험하기 위해 반드시 필요한 기능
  Support   Core 기능 사용을 돕는 최소 기능
  Later     없어도 MVP 경험이 성립하는 기능
  Remove    핵심 문제 해결과 직접 관계없는 기능

와이어프레임에는 기본적으로 **Core + 필요한 Support 기능만 포함**합니다.

## 4. 사용자 플로우

전체 서비스 구조보다 핵심 플로우의 완결성을 우선합니다.

-   사용자는 어디에서 시작하는가?
-   어떤 행동을 해야 하는가?
-   다음 단계로 이동하는 조건은 무엇인가?
-   최종적으로 어떤 결과를 얻는가?
-   결과 이후 사용자가 할 수 있는 최소 행동은 무엇인가?

가능하면 핵심 플로우는 하나의 명확한 경로로 설계합니다.

## 5. 화면별 역할

각 화면은 하나의 주요 목적을 가져야 합니다.

-   이 화면의 목적은 무엇인가?
-   사용자가 반드시 봐야 하는 정보는 무엇인가?
-   사용자가 해야 하는 핵심 행동은 무엇인가?
-   행동 후 어디로 이동하는가?

핵심 목적을 설명하기 어려운 화면은 삭제하거나 다른 화면과 통합할 수
있는지 검토합니다.

## 6. 정보 우선순위

MVP에서는 정보량보다 **핵심 판단 정보가 빠르게 전달되는 것**이
중요합니다.

-   가장 중요한 정보가 먼저 보이는가?
-   사용자가 다음 행동을 결정하는 데 필요한 정보가 충분한가?
-   설명 없이도 주요 콘텐츠와 CTA의 관계를 이해할 수 있는가?
-   핵심 경험과 관련 없는 정보가 과도하게 포함되어 있지 않은가?

## 7. CTA와 인터랙션

사용자가 다음에 무엇을 해야 하는지 명확해야 합니다.

-   Primary CTA가 명확한가?
-   CTA 문구만으로 행동 결과를 예상할 수 있는가?
-   불필요한 선택지를 제공하고 있지 않은가?
-   행동 후 즉각적인 피드백을 받을 수 있는가?
-   핵심 플로우를 방해하는 추가 액션은 없는가?

## 8. 최소 상태 설계

MVP에서도 핵심 플로우를 막을 수 있는 상태는 반드시 설계합니다.

  상태      설계 필요 기준
  --------- ----------------------------------------------------------
  Default   반드시 필요
  Loading   처리 시간이 발생하는 기능이면 필요
  Success   핵심 행동 완료 결과가 있으면 필요
  Error     실패 시 사용자가 진행할 수 없으면 필요
  Empty     데이터가 없을 가능성이 높고 핵심 경험에 영향을 주면 필요

모든 상태를 설계할 필요는 없습니다. **핵심 플로우가 중단되는 상황만 우선
대응**합니다.

## 9. 입력과 결과

입력형 서비스라면 최소한 다음을 확인합니다.

-   어떤 정보가 반드시 필요한가?
-   입력값을 어디까지 줄일 수 있는가?
-   잘못된 입력을 최소한으로 방지할 수 있는가?
-   입력 이후 어떤 결과를 제공하는가?
-   결과가 사용자의 문제 해결과 직접 연결되는가?

입력 단계가 길다면 한 번 더 축소할 수 있는지 검토합니다.

## 10. 구현 가능성

와이어프레임 단계에서도 개발 난도를 함께 고려합니다.

-   이 기능이 실제로 구현 가능한가?
-   구현 난도 대비 사용자 가치가 높은가?
-   더 단순한 방식으로 같은 경험을 만들 수 있는가?
-   외부 API나 AI 기능에 의존하는 부분은 무엇인가?
-   구현이 어려운 경우 데모 가능한 대체 방식이 있는가?

디자인 완성도보다 **실제로 동작하는 흐름**을 우선합니다.

## 11. 데모 시나리오

해커톤 MVP는 실제 사용 흐름과 함께 데모 흐름도 고려합니다.

-   어떤 화면에서 제품의 핵심 가치가 가장 잘 드러나는가?
-   심사자가 처음부터 핵심 가치까지 도달하는 흐름이 짧은가?
-   데모 중 설명 없이도 주요 인터랙션이 이해되는가?
-   핵심 기능이 안정적으로 재현 가능한가?
-   데모에 필요하지 않은 화면이 포함되어 있지 않은가?

## 최종 체크

1.  핵심 사용자가 누구인지 명확한가?
2.  해결하려는 문제가 화면 흐름에서 드러나는가?
3.  핵심 가치를 경험하는 순간이 명확한가?
4.  그 순간까지 필요한 최소 화면만 포함했는가?
5.  각 화면의 역할과 Primary CTA가 명확한가?
6.  핵심 플로우가 시작부터 결과까지 끊기지 않는가?
7.  실패 시 진행이 막히는 주요 상태를 처리했는가?
8.  없어도 되는 기능이나 화면을 더 제거할 수 없는가?
9.  현재 개발 리소스로 구현 가능한가?
10. 데모에서 핵심 가치가 짧고 명확하게 전달되는가?
