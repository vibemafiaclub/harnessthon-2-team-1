# STEP 2 — 정보구조

산출물: `ia.yaml`
템플릿: `templates/ia.template.yaml`
스키마: `schemas/ia.schema.json`

## 순서를 지킨다: 엔티티 먼저, 화면은 나중

화면부터 그리면 데이터 구조가 화면에 끌려다니고, 나중에 화면 간 데이터 불일치가 생긴다.
**엔티티 → 관계 → 화면** 순으로 간다.

## 1. 엔티티 도출

`definition.md`의 `REQ-`를 훑어 명사를 뽑는다. 각 엔티티에 `ENT-` 번호를 부여하고 다음을 정의한다.

- **필드** — 이름, 타입, 필수 여부. 화면에 보이는 것만이 아니라 상태 관리에 필요한 것도 포함.
- **관계** — 다른 엔티티와 1:1 / 1:N / N:M 중 무엇인가.
- **소유자** — 누가 만들고 누가 수정하는가 (`ROLE-` 참조).

### N:M 관계는 표시하고 넘어가지 않는다

N:M이 하나라도 나오면 `RISK-01`(다대다 귀속 모호성)이 해당된다. 이때 세 가지를 결정한다.

1. 중복 소속을 허용하는가
2. 허용한다면 목록에서 중복 노출되는가, 대표 분류를 지정하는가
3. 한쪽에서 지우면 다른 쪽은 어떻게 되는가

결정하지 않고 넘어가면 STEP 5에서 반드시 걸린다.

## 2. 화면 도출

엔티티와 `REQ-`를 교차해서 화면을 뽑는다. 각 화면에 `SCR-` 번호를 부여한다.

각 화면에 채울 항목:

| 항목 | 설명 |
|---|---|
| `name` | 화면 이름 |
| `purpose` | 이 화면이 책임지는 것 한 문장 |
| `roles` | 접근 가능한 역할 (`ROLE-`) |
| `entities` | 다루는 엔티티 (`ENT-`) |
| `requirements` | 충족하는 요구사항 (`REQ-`) |
| `entry_points` | 어디서 들어오는가 |
| `key_info` | 반드시 보여야 하는 정보 (레이아웃 아님) |
| `states` | 상태 변형 목록 |

### 레이아웃을 쓰지 않는다

`key_info`는 "무엇이 보여야 하는가"까지다. "상단에 카드 3개를 가로로"는 다음 하네스의 몫이다.

- 나쁨: `좌측 사이드바에 그룹 목록, 우측에 카드 그리드`
- 좋음: `그룹별 인원 수, 미회신 인원 수, 다음 모임 예정일`

### 상태 변형은 화면마다 반드시 쓴다

최소한 다음을 검토한다. 해당 없으면 없다고 판단하되, 검토는 한다.

- 빈 상태 (`RISK-07`) — 목록 화면이면 필수
- 로딩
- 에러
- 부분 완료 (`RISK-08`)
- 권한 없음
- 대량 데이터 (`RISK-06`) — 최대 건수에서 무엇이 필요한가

### 모달·시트

독립 화면으로 셀지 부속으로 셀지 애매하면, **뒤로가기로 이전 화면에 돌아가는가**로 판단한다. 돌아가면 부속(`SCR-07.1`), 아니면 독립(`SCR-08`).

## 3. 구조 배치

화면들을 내비게이션 구조에 배치한다. 뎁스와 진입 순서를 명시한다.
`RISK-10`(미인증 진입)이 해당되면 **미인증 사용자용 구조를 별도 트리로 분리한다.** 로그인 사용자 화면을 재사용하지 않는다.

## 4. 자체 점검

- [ ] 모든 `ENT-`가 최소 하나의 `SCR-`에서 다뤄지는가
- [ ] 모든 `SCR-`가 최소 하나의 `REQ-`를 참조하는가 (아니면 왜 필요한 화면인가)
- [ ] 목록 성격의 화면에 빈 상태가 전부 기재되었는가
- [ ] `key_info`에 레이아웃 표현이 섞이지 않았는가
- [ ] N:M 관계에 대한 세 가지 결정이 기록되었는가
