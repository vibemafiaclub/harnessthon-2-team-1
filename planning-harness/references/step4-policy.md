# STEP 4 — 정책

산출물: `policy.md`
템플릿: `templates/policy.template.md`

정책은 **화면에 그려지지 않지만 개발자가 물어보는 것**들이다. 여기서 안 정하면 개발 단계에서 개발자가 임의로 정하게 되고, 그 결과가 클라이언트 기대와 어긋난다.

각 항목에 `POL-` 번호를 부여한다.

## 1. 권한 정책

`users.md`의 권한을 행동 단위로 구체화한다. 표로 쓴다.

| 행동 | ROLE-01 | ROLE-02 | ROLE-03 |
|---|---|---|---|
| 지인 등록 | 가능 | 가능 | 불가 |
| 상대가 등록한 지인 수정 | 조건부 | 조건부 | 불가 |

"조건부"가 나오면 조건을 반드시 아래에 서술한다. 조건부를 조건 없이 남기지 않는다.

## 2. 상태·예외 정책

`flows.yaml`에서 나온 예외 처리 규칙을 확정한다.

- 마감 후 미응답자 처리 (`RISK-02`)
- 충돌 발생 시 차단인가 경고인가 (`RISK-03`)
- 취소 가능 단계와 취소 후 처리 (`RISK-09`)
- 우회 경로 사용 조건과 사용 주체 (`RISK-05`)

## 3. 데이터 정책

- 중복 소속 허용 여부와 삭제 시 연쇄 처리 (`RISK-01`)
- 삭제가 실제 삭제인가 숨김인가
- 완료 항목 보관 기간과 위치 (`RISK-12`)
- 최대 건수 제한 (`RISK-06`)

## 4. 알림 정책 (`RISK-11`)

표로 쓴다. 사건 → 수신자 → 채널 → 사용자 제어 가능 여부.

| 사건 | 수신자 | 채널 | 끌 수 있는가 |
|---|---|---|---|

채널이 미정이면 `TBD:`로 남긴다. 임의로 "푸시 알림"이라고 쓰지 않는다. 채널 선택은 비용과 개발 범위를 바꾼다.

## 5. 비기능 정책

원본에 있는 것만 쓴다. 없으면 `TBD:`로 남기고 클라이언트 확인 항목에 넣는다.

- 지원 브라우저·디바이스
- 접근성 준수 수준
- 개인정보 보관·파기 (연락처를 다루면 필수 검토)
- 성능 기준

## 6. 자체 점검

- [ ] 권한표에 "조건부"가 조건 서술 없이 남아 있지 않은가
- [ ] `flows.yaml`의 모든 `exceptions`가 어떤 `POL-`로 연결되는가
- [ ] 알림 표의 채널이 지어낸 값이 아닌가
- [ ] 개인정보를 다루는 서비스인데 관련 정책이 비어 있지 않은가
