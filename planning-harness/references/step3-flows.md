# STEP 3 — 플로우와 상태

산출물: `flows.yaml`
템플릿: `templates/flows.template.yaml`
스키마: `schemas/flows.schema.json`

## 1. 상태 정의 먼저

플로우보다 상태를 먼저 정의한다. 플로우는 상태를 옮기는 행위이기 때문이다.

핵심 엔티티(보통 1~2개)에 대해 `ST-` 번호로 상태를 정의하고, 전이를 그린다.

각 전이에 채울 항목:

| 항목 | 설명 |
|---|---|
| `from` / `to` | 상태 (`ST-`) |
| `trigger` | 무엇이 일어나면 (사용자 행동 / 시간 경과 / 외부 이벤트) |
| `actor` | 누가 (`ROLE-`) |
| `screen` | 어느 화면에서 (`SCR-`) |
| `notify` | 이 전이로 누구에게 알리는가 (`RISK-11`) |

### 반드시 검토할 전이

정방향만 그리고 끝내면 기획이 절반이다. 다음을 빠뜨렸는지 확인한다.

- **시간 경과 전이** — 마감·만료 (`RISK-02`). 사용자 행동 없이 상태가 바뀌는 경로.
- **역방향 전이** — 취소·되돌리기 (`RISK-09`). 확정된 것을 되돌리는 경로.
- **우회 전이** — 중간 상태를 건너뛰는 긴급 경로 (`RISK-05`).
- **부분 상태** — 완료도 미완료도 아닌 중간 (`RISK-08`).

### 종료 상태

모든 상태는 최종적으로 어딘가에서 끝나야 한다. 끝난 뒤 어떻게 되는지(`RISK-12` 이력·아카이브)를 정의한다.
빠져나갈 수 없는 상태(dead end)가 있으면 설계 오류다.

## 2. 플로우 작성

역할별 주요 시나리오를 `FLW-` 번호로 정의한다. 5~8개가 적정하다.

각 플로우:

```yaml
- id: FLW-02
  name: 모임 일정 조율
  role: ROLE-01
  trigger: 모임 편성 완료 후
  steps:
    - screen: SCR-06
      action: 날짜 후보 3개 선택, 회신 마감일 설정
      result: ST-01 (회신 대기)로 전이
  outcome: 전원 회신 완료 시 ST-02
  exceptions:
    - condition: 마감까지 미회신자 존재
      handling: SCR-07에서 마감 연장 또는 미회신자 제외 후 확정 (POL-04)
```

- 모든 스텝은 `SCR-`를 참조한다. 참조할 화면이 없으면 STEP 2로 돌아가 화면을 추가한다.
- `exceptions`를 비워두지 않는다. 예외 없는 플로우는 대개 예외를 생각하지 않은 플로우다.

### 플로우 커버리지

역할별로 최소 하나씩은 있어야 한다. 특히 `RISK-10`이 해당되면 **미인증 사용자 전용 플로우를 반드시 따로 쓴다.** 이 플로우는 로그인 플로우와 진입점부터 다르다.

**첫 진입(온보딩) 플로우는 여기서 쓰지 않는다.** 가입 → 첫 설정 → 첫 가치까지의 경로는 STEP 4에서 `onboarding.yaml`로 따로 다룬다. 여기서는 "이미 쓰고 있는 사용자"의 시나리오만 쓴다. 다만 온보딩이 끝나면 이어질 플로우(보통 핵심 플로우의 첫 전이)가 무엇인지는 의식해 둔다 — STEP 4의 `first_value`가 그것을 가리킨다.

## 3. 자체 점검

- [ ] 모든 `ST-`에 진입 전이와 이탈 전이가 있는가 (dead end 없음)
- [ ] 시간 경과 전이가 하나 이상 있는가 (`RISK-02` 해당 시)
- [ ] 역방향 전이를 검토했는가 (`RISK-09`)
- [ ] 모든 `ROLE-`에 최소 하나의 `FLW-`가 있는가
- [ ] 모든 플로우 스텝이 실재하는 `SCR-`를 참조하는가
- [ ] `exceptions`가 비어 있는 플로우가 없는가
